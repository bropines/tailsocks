# Как участвовать в разработке TailSocks

Прочитайте это один раз перед первым патчем. Здесь коротко и только то, что
касается именно этого репозитория.

## 1. С чем вы имеете дело

TailSocks — это Android-клиент Tailscale, который запускает настоящий
`tailscaled` в userspace, поэтому приложение работает вообще без разрешения
Android на VPN. Интерфейс написан на Kotlin/Compose, мост между приложением и
демоном — модуль Gomobile (`appctr/`), а сам демон — это upstream Tailscale плюс
небольшой набор локальных патчей. Режимы TUN и Root надстроены поверх этого
ядра, а не заменяют его.

**Главное правило, из которого следует почти вся структура кода: Go-демон — это
отдельный процесс, а не библиотека внутри приложения.** `libtailscale.so` и
`libtailscale_cli.so` — position-independent executables (PIE), которые
приложение запускает через `fork/exec` из `jniLibs`, а дальше общается с
работающим процессом по unix-сокету `files/tailscaled.sock` через LocalAPI v0.
Управление демоном никогда не оборачивает CLI-бинарник, и Kotlin никогда не
линкует демон в себя. Если хочется позвать Go-функцию напрямую из Kotlin —
почти всегда правильный ответ это вызов LocalAPI или новый метод моста
`appctr`, а не новая связь по коду.

## 2. Сборка

Два этапа, строго в этом порядке. Gradle только *упаковывает* готовые Go- и
C-артефакты, он их не собирает.

```bash
git clone --recurse-submodules https://github.com/bropines/tailsocks.git
cd tailsocks

# Этап 1 — ядро на Go и JNI-мост (нужен ANDROID_NDK_HOME)
cd appctr && bash build.sh && cd ..

# Этап 2 — APK
./gradlew app:assembleDebug
```

`appctr/build.sh` скачивает версию Tailscale, зафиксированную в
`appctr/TAILSCALE_VERSION` (сейчас `v1.102.1`), накладывает все патчи из
`appctr/patches/`, кросс-компилирует два PIE-бинарника под `arm64-v8a`,
`armeabi-v7a`, `x86` и `x86_64` в `app/src/main/jniLibs/` и собирает
`appctr/tmp/appctr.aar`.

**Изменение в Go без первого этапа даёт APK, в котором этого изменения нет.**
Файлы `.so` и `.aar` — это заранее собранные входные данные, и Gradle спокойно
упакует вчерашние. Задача `verifyGoBridgeFresh` (подцеплена к `preBuild`)
сравнивает время изменения `appctr/tmp/appctr.aar` со всеми `appctr/*.go` и всем
содержимым `appctr/patches/`: release-сборка при устаревшем мосте **падает**,
debug-сборка только предупреждает. Относитесь к этому предупреждению как к
ошибке — однажды целый день исправлений в Go уехал в APK, которого в нём не
было, ради этого проверка и появилась.

Для release-сборки нужен настоящий keystore и все четыре переменные; начиная с
4.0.0 сборка отказывается подписывать debug-ключом (release-APK, подписанный
одноразовым ключом, потом невозможно обновить нормально подписанным — Android не
принимает смену сертификата, и выход только один: удалить приложение вместе со
всем его состоянием):

```bash
KEYSTORE_FILE="$PWD/tailsocks.jks" KEYSTORE_PASSWORD=... \
KEY_ALIAS=... KEY_PASSWORD=... ./gradlew app:assembleRelease
```

ABI-сплиты включены, поэтому на выходе универсальный APK плюс по одному на
каждую ABI в `app/build/outputs/apk/<debug|release>/`.

Не коммитьте сгенерированное и приватное: бинарники `.so`, `appctr/tmp/`,
`appctr/tailscale_src/`, `appctr/orig/` и keystore — всё это в `.gitignore` и
должно там остаться. Строки интерфейса в этом репозитории ведутся руками:
добавляйте строку в `app/src/main/res/values/strings.xml` **и** её перевод в
`app/src/main/res/values-ru/strings.xml` одним коммитом. Русскую локаль ничто не
пересобирает — `.github/crowdin.yml` в репозитории есть, но ни один workflow его
не использует, — а непереведённый русский интерфейс здесь считается дефектом, а
не отложенной работой.

## 3. Изменения демона — это патчи, а не правки

`appctr/tailscale_src/` — **сгенерированный** каталог, он в `.gitignore`: это
чистый upstream Tailscale с наложенными по алфавиту `appctr/patches/*.patch`
(`01-enable-socks-android` … `16-android-somark`, сейчас шестнадцать штук). В
`appctr/orig/` лежит чистая копия, относительно которой считается diff. Источник
истины — файлы патчей; дерево исходников это черновик.

Рабочий цикл:

1. Сначала прочитайте upstream-файл. Стройте решение вокруг того, как это уже
   сделано в Tailscale, — чистая копия лежит рядом, в `appctr/orig/`.
2. Правьте в `appctr/tailscale_src/`, собирайте, итерируйте.
3. Пересоберите набор патчей: `./appctr/patches/recreate_patches.sh`. Скрипт
   удаляет `patches/*.patch` и заново снимает diff `tailscale_src` против
   `orig` — по файлам, а для taildrop/taildrive/net — по каталогам.
4. Проверьте с нуля: `cd appctr && bash build.sh --clean`. Без `--clean`
   `build.sh` видит существующий `tailscale_src/` и **вообще пропускает
   наложение патчей**, так что сломанный патч обнаружится только у того, кто
   соберёт следующим.

Два требования к патчу:

* Он должен накладываться на чистые исходники без fuzz. `build.sh` вызывает
  `patch -p1 --batch --forward -F0`, поэтому смена версии, сдвинувшая контекст,
  роняет сборку, а не вставляет ханк не туда.
* Он не должен быть пустым. `build.sh` прерывается на патче нулевого размера,
  потому что GNU `patch` принимает такой файл и выходит с кодом 0 — потерянное
  исправление уехало бы молча.

Если вы правите файл, который `recreate_patches.sh` ещё не диффит, добавьте для
него секцию в том же коммите. Иначе ваша работа исчезнет при первой же чистой
сборке.

Смена версии Tailscale — это правка `appctr/TAILSCALE_VERSION`; `build.sh` сам
заметит её и принудительно перекачает и перепатчит исходники.

## 4. Три режима туннеля

Настройки → Режим туннеля, выбирается ровно один:

| Режим | Как трафик попадает внутрь | Что нужно |
|---|---|---|
| **Proxy** (по умолчанию) | Приложения сами настраиваются на локальный SOCKS5/HTTP-прокси и локальный DNS. Ничего не перехватывается. | Ничего — ни разрешения VPN, ни root |
| **VPN (TUN)** | Дескриптор Android `VpnService` отдаётся нативному `hev-socks5-tunnel` (`app/src/main/jni/`), который заворачивает трафик в тот же локальный SOCKS5. | Системное разрешение на VPN |
| **Root** | Демон запускается через `su` на настоящем интерфейсе ядра `tailscale0`, с policy routing в таблице `53` и цепочками `TAILSOCKS_MARK` / `TAILSOCKS_DNS`. Слот Android VPN остаётся свободным. | Magisk / KernelSU / APatch |

**Изменение в одном режиме не должно менять поведение двух других.** Общего у
них — демон и локальные прокси, и больше ничего; при этом легко «починить» один
режим, переложив что-нибудь в эту общую середину. Конкретно:

* Proxy обязан продолжать работать без разрешения на VPN и без root. Ради этого
  приложение и существует — не делайте так, чтобы общий код зависел от
  `VpnService` или от `su`.
* Маршрутизация Root Mode живёт в `core/RootUtils.kt`, и почти вся она — это
  *policy routing* через `ip rule` / `ip route`, а не iptables: правила тайлнета
  в таблицу `53` с priority 100, catch-all в таблицу демона `52` с priority 200,
  исключения приложений `uidrange … goto` с priority 190 и `throw`-маршруты для
  локальной сети и чужого CGNAT. На iptables остаются только маркировка и DNAT,
  и только внутри `TAILSOCKS_MARK` / `TAILSOCKS_DNS`: никогда не пишите голый
  `--set-mark`, в `OUTPUT` — только защищённые переходы в эти цепочки, в
  `FORWARD` — только пара ACCEPT для `tailscale0`. Не возвращайте цепочку
  bypass на mangle-марках: 4.0 удалила старую `TAILSOCKS_BYPASS`, потому что
  метка, поставленная в mangle `OUTPUT`, приходит уже после того, как выбраны
  маршрут и адрес источника. Правила разделены на уровни: T1 (доступность тайлнета) уживается с чем угодно, а T2 (перехват
  маршрута по умолчанию) и T3 (DNS всего устройства) забирают устройство целиком
  и потому имеют ровно одного владельца. Прежде чем трогать T2 или T3, прочитайте
  `docs/ROOT_RU.md`, разделы 4–5: описанная там логика сосуществования — это то, что
  не даёт увести приложения у другого VPN-клиента.
* TUN работает — и в 4.0 продолжает работать — на `hev-socks5-tunnel`. Перевод
  на нативный TUN, где `tailscaled` сам владеет дескриптором `VpnService`, — это
  план на 4.1 ([`docs/NATIVE_TUN_PLAN.md`](docs/NATIVE_TUN_PLAN.md) —
  единственный документ проекта без русского перевода), а не код:
  не вносите его половину и не описывайте его как уже существующий.

Напишите в pull request, в каких режимах вы проверяли. «Только proxy» —
нормальный ответ; молча не проверить — нет.

## 5. Коммиты и changelog

**Заголовки** — в стиле conventional commits, на английском, как в `git log`:

```
feat(root): health-gate the DNS redirect, guard foreign CGNAT, leave netd's table space
fix(ui): stop the DNS test button from covering its own title
perf(root): react to another tunnel at once instead of on the next tick
docs: hand off what is left — Root Mode device checks and the CLI binary
```

* Префикс: `feat`, `fix`, `docs`, `refactor`, `perf`, `style`, `chore`.
* Скоуп в скобках, по области — `(root)`, `(ui)`, `(core)`, `(dns)`, `(tun)`,
  `(build)`, `(appctr)`, `(security)`, `(patches)`. Опускайте его, только если
  изменение действительно общерепозиторное (`docs:`).
* Заголовок говорит, каким стало поведение, а не какой файл подвинули. После
  двоеточия со строчной буквы, без точки в конце; длина до ~90 символов —
  читаемая фраза лучше обрубленной метки.
* Тело коммита — про «почему» и про то, что ломается без этого. Для мелочей не
  нужно, для всего неочевидного обязательно. Код, комментарии, логи и сообщения
  коммитов пишутся по-английски независимо от языка обсуждения.

**Всё, что заметит пользователь, попадает в `CHANGELOG.md` тем же коммитом,
который меняет поведение** — не отдельным коммитом позже и не при выпуске
релиза. Запись идёт под самый верхний заголовок `## [X.Y.Z] - Unreleased`, в
подходящую группу `Added` / `Changed` / `Fixed` / `Security`. Заголовок, у
которого уже стоит дата, править нельзя: выпущенные разделы — это история.

Changelog пишется для пользователей и для того, кто выпускает релиз. Пишите, что
изменилось и почему это важно; без имён классов, путей к файлам, констант, id
ресурсов и полей API. Чтобы поймать нужный тон, сравните заголовок коммита с его
строкой в разделе `[4.0.0]`.

**Версия вычисляется, а не пишется руками.** Gradle берёт `versionName` из
`git describe --tags --always --abbrev=0`, а `versionCode` из
`git rev-list --count HEAD` + 500, так что ни в одном файле нет номера версии,
который надо было бы поднимать. Релиз делается тегом `vX.Y.Z`, и в этот же
момент заголовок `Unreleased` переименовывается в `## [X.Y.Z] - YYYY-MM-DD`.
Это переименование обязательно: CI собирает описание GitHub-релиза, отыскивая в
`CHANGELOG.md` заголовок `## [<тег без v>]`, и тег без такого заголовка даёт
релиз с пустым описанием. Теги ставит мейнтейнер — присылайте pull request в
`main` и тег не трогайте.

## 6. Тестирование

Сразу о том, чего в проекте нет: **юнит-тестов для Android-части нет вообще, и
инструментальных тестов тоже.** Зелёный CI не означает, что ваше изменение
работает.

Что можно проверить без устройства:

* `cd appctr && go test ./...` — собственные тесты Go-моста (сейчас
  `extraargs_test.go`).
* `gofmt` по `appctr/` — CI падает на неотформатированном Go. `appctr/build.sh`
  сам делает `gofmt -w *.go`, а `git config core.hooksPath .githooks` включает
  pre-commit-хук, который делает то же самое перед коммитом.
* `./gradlew app:assembleDebug` — компиляция, и это, честно говоря, почти всё,
  что в Kotlin-части проверяется автоматически.
* Если вы добавили `external fun`, соберите release и дайте отработать
  `verifyReleaseNativeMethods`: задача падает, когда R8 вырезал нативный метод, —
  иначе это превращается в падение `System.loadLibrary` уже во время работы. Для
  новых нативных методов нужен обычный `-keep` для `native <methods>` в
  `app/proguard-rules.pro`.

Что реально требует устройства:

* Всё, что связано с JNI и нативным кодом: TUN-движок и ByeDPI проверяются
  только в рантайме, а поведение R8 в debug и release различается.
* Жизненный цикл foreground-сервиса, плитка Quick Settings, виджеты, SAF.
* **Весь Root Mode.** Policy routing, цепочки iptables и логику сосуществования
  с другим VPN-клиентом негде проверить, кроме рутованного телефона; работа над
  сосуществованием в 4.0.0 проверялась на рутованном Redmi (APatch), в том числе
  через настоящую перезагрузку. Инструменты для этого: **Настройки →
  Диагностика и разработчику → «Проверить маршрутизацию»**, вкладка **ROOT** на
  экране логов и `tools/root-debug.sh`, запущенный на устройстве под `su`, —
  он печатает полный снимок состояния.
