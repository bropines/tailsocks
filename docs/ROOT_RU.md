# Интеграция с Root и Системная Служба в TailSocks

TailSocks поддерживает расширенный **Root-режим** для Android-устройств с правами суперпользователя (**Magisk**, **KernelSU** или **APatch**). Root-режим позволяет демону `tailscaled` работать в качестве полноценного системного демона независимо от жизненного цикла Android UI, автоматически запускаться при загрузке устройства и предоставлять официальный консольный интерфейс `tailscale` CLI в терминальной среде.

---

## ⚡ Ключевая Архитектура и Возможности

### 1. Автозапуск Системной Службы через `service.d` (`tailscaled.sh`)
* **Путь:** `/data/adb/service.d/tailscaled.sh`
* **Запуск:** Выполняется автоматически Magisk / KernelSU / APatch на ранней стадии загрузки (`late_start` фаза) от имени `root` (UID 0).
* **Авто-определение Директории Состояния:** Динамически ищет существующие профили аккаунтов в `/data/data/io.github.bropines.tailscaled/files/states/` (по умолчанию `default` или `root`).
* **Управление Сокетом и Логами:** Использует сокет `/data/data/io.github.bropines.tailscaled/files/tailscaled.sock` с правами `0666` (благодаря встроенному патчу safesocket в ядре TailSocks). Логи демона (`tailscaled.log`) автоматически ротируются при превышении 2 МБ.
* **Передача Прокси и Control Plane:** Считывает переменные окружения из файла `/data/adb/tailsocks/control_proxy.env`, принадлежащего root (включая `ALL_PROXY`, `HTTP_PROXY`, `HTTPS_PROXY` и разрешённые IP через `TS_STATIC_HOSTS`). Приложение записывает его через `su` при каждом запуске root-демона; скрипт принимает только строки вида `export NAME='value'` и никогда не исполняет ничего из каталога данных приложения — туда может писать само приложение или восстановленный бэкап.
* **Маршрутизация при загрузке:** Как только появляется `tailscale0`, скрипт ставит уровень T1 — и больше ничего (раздел 4 ниже): правила tailnet (маскированный fwmark `0x1000000/0x1000000` → таблица `53`, правила по адресу назначения, цепочка `TAILSOCKS_MARK`, пара правил FORWARD для `tailscale0`, IPv4 и IPv6) плюс удаление остатков 3.5.x («голая» метка `1099`, прямые записи в `OUTPUT`). Ни catch-all для exit-ноды, ни системный DNS-редирект скрипт не ставит: он не может поставить то, что делает эти два уровня безопасными. `throw`-маршруты для локальной сети и исключения приложений требуют разрешения имён пакетов в uid'ы, а `PackageManager` на стадии `late_start` ещё не существует; другой VPN-клиент к этому моменту тоже не запущен, так что проверка соседства здесь всегда отвечала бы «устройство свободно». Захват без своих исключений хуже, чем отсутствие захвата, — именно так перезагрузка с выбранной exit-нодой уносила в туннель локальную сеть и приложения из списка исключений. Оба уровня, действующие на всё устройство, ставит приложение — вместе с исключениями и после проверки соседства — на первом же тике в состоянии `Running` (разделы 4 и 5). **Цена:** при выключенном переключателе «Работать в фоне» приложение при загрузке не стартует вовсе, поэтому после перезагрузки exit-ноды и системного MagicDNS не будет до тех пор, пока вы не откроете TailSocks: узел поднят и адреса tailnet доступны, но больше ничего на устройстве через него не идёт. Копия скрипта в `service.d` обновляется автоматически при обновлении приложения (раздел 3).

### 2. Интеграция с Tailscale CLI (`tailscale_cli.sh`)
* **Пути установки CLI-обёртки:**
  * `/data/adb/service.d/tailscale` (Исполняемый фаллбэк)
  * `/data/adb/modules/tailscaled/system/bin/tailscale` (Оверлей-модуль Magisk)
  * `/product/bin/tailscale` (Оверлей для раздела `/product/bin`)
  * `/system/bin/tailscale` (Прямая ссылка в `/system/bin`, если раздел доступен для записи)
* **Принцип работы:** Оборачивает нативный бинарник `libtailscale_cli.so` из установленного пакета приложения и автоматически подставляет аргумент `--socket=/data/data/io.github.bropines.tailscaled/files/tailscaled.sock` к каждой команде.
* **Применение:** Позволяет выполнять стандартные команды `tailscale` в Termux, `su`-шелле, ADB-шелле и скриптах.

### 3. Автоматическое Обновление при Обновлении Приложения (`BootReceiver`)
* **Отслеживаемые События:** `ACTION_BOOT_COMPLETED`, `QUICKBOOT_POWERON` и `ACTION_MY_PACKAGE_REPLACED`.
* **Логика Обновления:** При обновлении TailSocks (замене APK) `BootReceiver` автоматически обновляет скрипты службы `service.d` и CLI-обёртку из ассетов. Это гарантирует, что пути к нативным библиотекам `libtailscale.so` и `libtailscale_cli.so` в `/data/app/...` всегда актуальны и соответствуют новой версии без необходимости ручной переустановки.

### 4. Нативная маршрутизация TUN (`tailscale0`)

При включённом **Native Linux TUN** демон создаёт настоящий интерфейс ядра
`tailscale0`, оставляя слот Android VPN свободным. TailSocks настраивает
policy-routing вокруг него после перехода демона в состояние `Running`.

Правила делятся на три уровня, и различает их одно — какую часть устройства
каждый забирает себе:

| Уровень | Из чего состоит | На что претендует |
|---|---|---|
| **T1 — доступность tailnet** | таблица `53`, два правила priority 100, цепочка `TAILSOCKS_MARK`, пара правил FORWARD для `tailscale0`, публикация в `/etc/hosts` и локальные SOCKS5/HTTP-прокси | только пакеты, которые это устройство шлёт на адрес tailnet |
| **T2 — захват маршрута по умолчанию** | catch-all с priority 200 в таблицу демона `52`, `throw`-маршруты для локальной сети, ослабление `rp_filter` и правила исключений приложений с priority 190, пробивающие в нём дыры | всё, что шлёт это устройство, пока выбрана exit-нода |
| **T3 — DNS всего устройства** | цепочка `TAILSOCKS_DNS` и два её хука в `nat OUTPUT` | каждый пакет на порт 53 на устройстве |

T1 уживается с чем угодно по построению. T2 и T3 претендуют на всё устройство и
потому имеют ровно одного владельца: когда слотом Android VPN уже владеет другой
клиент, они отдаются ему — целиком или до тех приложений, которые тот клиент
пропускает мимо себя. Три состояния и граница между ними — в разделе 5.

Все три уровня ставит приложение, на первом же тике в состоянии `Running`.
Загрузочный скрипт ставит только T1: всё, что делает T2 и T3 безопасными —
`throw`-маршруты для локальной сети, исключения приложений, исключение чужого
DNS, — требует разрешения имён пакетов в uid'ы, а `PackageManager` на стадии
`late_start` недоступен (раздел 1).

* **Таблица `53`** содержит маршрут `100.64.0.0/10` (и `fd7a:115c:a1e0::/48`)
  через `tailscale0`. Трафик направляется в неё двумя правилами с priority 100:
  `ip rule … fwmark 0x1000000/0x1000000 table 53` для помеченных пакетов и
  `ip rule … to 100.64.0.0/10 iif lo table 53` (и IPv6-диапазон) по адресу
  назначения. Второе нужно для собственных сокетов демона: метка ставится в
  `mangle OUTPUT` *после* того, как ядро уже выбрало source-адрес из таблицы
  Wi-Fi, так что без него запросы демона к split-DNS-резолверу на пире уходили
  в `tailscale0` с Wi-Fi-адресом источника и не получали ответа. `iif lo`
  ограничивает это правило пакетами, которые устройство порождает само: пакет,
  просто проходящий через телефон (от привязанного клиента, через subnet-роутер),
  остаётся на попечении правил Android, а не забирается нами и не отвечается с
  нашего адреса источника. Правилу по метке такая оговорка не нужна: метка
  ставится только в `mangle OUTPUT`, куда транзитные пакеты не попадают.

  Все сборки до 4.0.0 использовали таблицу `1099`. netd называет таблицы своих
  сетей номером интерфейса плюс 1000, так что на телефоне, у которого индекс
  интерфейса когда-либо доходил до 99, эта таблица принадлежит живой сети — а
  очистка её раньше сбрасывала целиком. Больше в неё ничего не пишется; каждое
  применение и каждая остановка по-прежнему удаляют из неё то, что оставила
  старая версия, — по содержимому и никогда через flush. Если перед вами
  устройство, на котором 4.0.0 ещё не запускалась, смотрите в `1099`.
* **`TAILSOCKS_MARK`** (mangle, вызывается из `OUTPUT` для диапазонов tailnet)
  ставит эту метку через `--set-xmark 0x1000000/0x1000000`. Через маску
  трогается лишь один старший бит: Android хранит в fwmark собственное решение
  о маршрутизации (netId в младших 16 битах, выше — флаги explicit/protect/
  permission), и «голый» `--set-mark 1099`, использовавшийся до 4.0.0, затирал
  его целиком, ломая маршрутизацию, когда сетью по умолчанию владел другой VPN.
  Старая метка и старые правила без цепочек удаляются автоматически при первом
  запуске после обновления.
* **`TAILSOCKS_DNS`** (nat, вызывается из `OUTPUT` для порта 53 UDP/TCP)
  перенаправляет системный DNS на MagicDNS (`100.100.100.100`). Два класса
  трафика исключаются до редиректа, в этом порядке:
  * диапазон tailnet `100.64.0.0/10` — чтобы Split DNS-резолверы на пирах
    оставались доступны напрямую;
  * собственные upstream-резолверы демона (`TS_DNS_FALLBACK`, берутся из
    настройки DNS fallback). Без этого запросы самого резолвера
    перенаправляются обратно в него же, и ни одно внешнее имя не резолвится.

  Редирект ставится **только** при включённом `accept-dns` (перенаправлять всё
  устройство на резолвер, который не отвечает, значит сломать DNS целиком) и
  отключается вручную переключателем **Системный DNS через MagicDNS** (Настройки
  → DNS). Он также отдаётся автоматически, когда устройством владеет другой
  VPN-клиент: целиком при полной уступке, а при частичной — только для сети
  этого клиента, и тогда в начале цепочки стоит `RETURN` по его netId (раздел 5).
  В любом случае этот переключатель больше не единственный выход из конфликта.

  Хук стоит на позиции 1 в `nat OUTPUT`, то есть адрес назначения переписывается
  уже **после** того, как ядро выбрало адрес источника. Поэтому чужие запросы
  должны покидать цепочку до DNAT, а не разбираться потом: пока устройством
  владел другой туннель, запросы его приложений приходили к нам с **его**
  адресом источника — это видно как поток `netstack inject ts-service:
  src=100.100.100.100 dst=<адрес чужого туннеля>` с частотой, достаточной, чтобы
  сработал ограничитель логов самого демона.
* **Exit-ноды, subnet-маршруты и таблица `52`.** Всё, что знает только демон,
  он пишет в собственную таблицу `52`: `/32` пиров, принятые subnet-маршруты,
  `100.100.100.100/32`, `default dev tailscale0` пока выбрана exit-нода и
  `throw`-маршруты для префиксов локальной сети при включённом *allow LAN
  access*. Приложение в эту таблицу не пишет, не очищает и не проверяет её —
  оно лишь добавляет одно постоянное правило рядом с правилами priority 100:

  ```
  200: from all fwmark 0x0/0x2020000 iif lo lookup 52
  ```

  Каждый непомеченный локально сгенерированный пакет сначала смотрит в таблицу
  52 и, если совпадения нет, проваливается в собственные правила Android (10000
  и выше). Поэтому включение и выключение exit-ноды целиком обрабатывает
  `router.Set()` демона, как на десктопном Linux: в приложении нет состояния
  exit-ноды и нечего переделывать при переходе Wi-Fi ↔ сотовая сеть. Безопасным
  это правило делают две вещи:

  * **Демон помечает собственные сокеты.** Каждый сокет, который tailscaled
    открывает сам (WireGuard/disco UDP, DERP, control plane, STUN, DNS
    fallback), несёт `SO_MARK 0x2000000` (бит 25, патч 16 — вне собственных
    бит fwmark Android 0–20 и отдельно от бита 24 приложения). Такие пакеты
    пропускают pref 200 и уходят в физическую сеть по правилам netd. Без метки
    default-маршрут таблицы 52 заглотил бы собственные пакеты туннеля и
    зациклил всё устройство — поэтому TailSocks ставит pref 200 **только
    после** того, как текущий запуск демона записал в лог `netns: SO_MARK
    0x2000000 set on tailscaled sockets` (одной непрерывной строкой; перед ней
    стоят префикс Go с датой и временем `YYYY/MM/DD HH:MM:SS` и префикс
    компонента, например `magicsock:`). Демон дописывает в один и тот же файл
    от запуска к запуску и в этой сборке не печатает собственного стартового
    баннера (`ts_omit_logtail`), поэтому «текущий запуск» — это всё после
    более поздней из двух строк: `TailSocks: daemon start`, которую оба способа
    запуска — загрузочный скрипт и приложение — пишут непосредственно перед
    стартом демона, и собственной строки демона
    `wgengine.NewUserspaceEngine(tun "tailscale0") ...`, которую любое ядро
    печатает при каждом старте прямо перед созданием движка (а вместе с ним и
    пробы). Лог просматривается с конца до этого начала запуска, сколько бы
    демон ни проработал, и строка пробы засчитывается, только если ниже неё
    найдено начало запуска — так что ни строка прежнего запуска, ни демон,
    перезапущенный вручную, не могут позаимствовать чужой вердикт. Но лог, который
    просто *молчит* — нет начала запуска вовсе или под ним нет строки пробы, —
    это не «нет»: лог ротируется, и у демона, работающего не первый день,
    стартовые строки давно уехали, из-за чего на живом устройстве exit-нода
    отключалась по причине, никак не связанной с маршрутизацией. В этом случае
    TailSocks спрашивает сам работающий процесс и засчитывает его, если
    `/proc/<pid>/exe` указывает внутрь `nativeLibraryDir` приложения: бинарь,
    который мы собираем, маркирует свои сокеты безусловно. Явно отрицательный
    вердикт, записанный *самим демоном*, так не перебивается, а если ни один из
    двух свидетелей недоступен, pref 200 не ставится. Во всех
    отрицательных случаях в ROOT-логе появляется `exit node unavailable: daemon
    does not mark sockets (<причина>)`, и на pref 200 ничего не ставится;
    маршрутизация
    tailnet через таблицу 53 от этого не зависит. Строки с пометкой
    `TailSocks:` пишут приложение и сам загрузочный скрипт — за строки демона
    они не считаются. Сам загрузочный скрипт эту проверку больше не делает: он
    не ставит правило priority 200, значит и проверять ему нечего.
  * **Маска учитывает бит `protectedFromVpn` Android** (`0x20000`) — тот же
    приём, что netd использует в собственных VPN-правилах: сокеты, которые
    Android намеренно держит вне VPN (проверки доступности сети, MMS/IMS,
    защищённые сокеты других VPN-приложений), тоже минуют exit-ноду. `iif lo`
    ограничивает правило исходящими lookup'ами, так что клиенты точки доступа
    остаются на правилах netd.

  Ответы на помеченные сокеты демона приходят по Wi-Fi/сотовой сети и проходят
  reverse-path-проверку с меткой 0, которая теперь через таблицу 52 указывает
  на `tailscale0`, — строгий `rp_filter` (1) отбросил бы их. Поэтому, если хоть
  один интерфейс в строгом режиме, `all` переводится в loose (2), прежнее
  значение сохраняется в `/data/adb/tailsocks/rp_filter.orig` и
  восстанавливается при очистке. Правило перечитывается после установки
  (бинарь `ip`, потерявший маску, оставил бы правило «совпадает со всем» — оно
  удаляется и о нём сообщается), а десктопные правила, оставшиеся от ядра до
  4.0 (`5210 lookup main`, `5230 lookup default`, `5250 unreachable`, `5270
  lookup 52`), удаляются по содержимому при каждой установке и при очистке.

  На Android роутер демона делает только то, что может только он: поднимает
  интерфейс, ставит адреса, пишет маршруты в таблицу 52. Он не ставит
  ip-правила `52xx` (таблицы `main`/`default` на Android пусты, так что
  десктопные правила либо зацикливают, либо роняют трафик) и вообще не трогает
  netfilter — метки Tailscale `0x40000`/`0x80000` совпадают с битами
  разрешений netd, а на части ядер отсутствует тип nft-цепочки `nat`; отсюда и
  брался прежний health-warning `router config failed`. Root-режим — только
  клиент: в нём это устройство не может быть exit-нодой или subnet-роутером.

* **Исключение отдельных приложений** — правило политики маршрутизации, а не
  правило файрвола. Root-режим по своей природе действует на всё устройство:
  DNS-редирект ловит порт 53 любого приложения, а catch-all с приоритетом 200
  отправляет в exit-ноду каждый непомеченный локальный пакет. Приложения из
  списка **Настройки → Режим туннеля → Исключенные приложения** (тот же список,
  что TUN-режим отдаёт в `addDisallowedApplication`: один список на оба режима)
  при каждой установке правил превращаются в uid'ы и получают правило вида:

  ```
  ip rule add uidrange 10234-10234 goto <первый приоритет netd> priority 190
  ```

  Приоритет цели не зашит в код: он читается из живого `ip rule show` — берётся
  наименьший приоритет, начиная с 10000. `goto` перепрыгивает через все наши
  правила и возвращает uid под управление самого Android. Правило перечитывается
  после установки: ядро **принимает** `goto` на несуществующий приоритет и потом
  молча его пропускает, поэтому неразрешившееся правило снимается, а в ROOT-лог
  пишется маркер.

  Прежняя версия дополнительно метила такие uid'ы bypass-битом демона в
  mangle-цепочке `TAILSOCKS_BYPASS`. Этой цепочки больше нет: метка в
  `mangle OUTPUT` выставляется уже после того, как ядро выбрало маршрут и адрес
  источника для соединения, поэтому исключения она не делала, а при отсутствии
  правила приоритета 190 превращала тихое бездействие в сломанный пакет —
  правильный интерфейс, адрес источника из тейлнета, в ответ тишина. При каждой
  установке правил цепочка по-прежнему отцепляется и удаляется, так что после
  обновления от неё ничего не остаётся.

  Про DNS исключённого приложения — честно. В начало `TAILSOCKS_DNS`, до правил
  DNAT, по-прежнему ставится `RETURN` по uid:

  ```
  iptables -t nat -A TAILSOCKS_DNS -m owner --uid-owner 10234 -j RETURN
  ```

  Но `-m owner --uid-owner` сравнивает uid **процесса-отправителя**, а на Android
  `getaddrinfo` обычного приложения отправляет системный резолвер от своего
  имени, а не приложение от своего. Значит это правило покрывает только те
  приложения, которые резолвят сами: собственный резолвер Chrome, клиенты
  DoH/DoT, `curl`. Обычное приложение через него не проходит, и его имена
  по-прежнему разрешает MagicDNS. Замер на устройстве это подтверждает: счётчик
  такого `RETURN` остаётся нулевым, пока счётчик DNAT растёт. Если системный
  резолвер нужен наверняка — выключайте **Системный DNS через MagicDNS**
  целиком.

  Что **не** исключается: правила приоритета 100 смотрят на адрес назначения,
  поэтому исключённое приложение по-прежнему достаёт адреса тейлнета через
  `tailscale0` — наружу возвращается только его маршрут по умолчанию. Имена
  MagicDNS для него разрешаются через публикацию в `/etc/hosts`, а домены
  split-DNS не разрешаются вовсе.

  Эти правила ставятся **только** вместе с тем catch-all, дырой в котором они
  являются, — в том числе при частичной уступке: что catch-all захватил, то
  исключение может вернуть обратно. При полной уступке не захватывается ничего,
  поэтому и правил исключения не ставится: такое правило перепрыгнуло бы и через
  правила чужого клиента и вынуло бы приложение из туннеля, в котором оно должно
  быть.

  Пакет, которого уже нет на устройстве, пропускается и называется в ROOT-логе.
  `-m owner` — необязательный модуль ядра (`xt_owner`): если его нет, правила
  `RETURN` отклоняются, а правила маршрутизации встают как обычно — то есть
  приложение оказывается вне туннеля, но его DNS остаётся перехваченным. Это
  тоже пишется в ROOT-лог. При пустом списке не генерируется вообще ничего.

Все правила живут в именованных цепочках — они идемпотентны, их видно через
`iptables -t nat -S TAILSOCKS_DNS` / `iptables -t mangle -S TAILSOCKS_MARK` /
при каждом запуске они заменяются как единое целое и снимаются одним махом при
остановке службы. Скрипт проверяет собственный результат (таблица заполнена,
DNS-цепочка существует), а не доверяет коду возврата шелла; после трёх
неудачных попыток он сдаётся и сообщает об этом в лог.

### 5. Соседство с другим VPN-клиентом

Все числа в этом разделе сняты с устройства, а не выведены умозрительно. Сырой
снимок — собственные правила netd, uid'ы, netId'ы, интерфейсы и DNS-серверы
вместе с командами, которыми они получены — лежит в
[`docs/research/foreign-vpn-measurements.md`](research/foreign-vpn-measurements.md)
(на английском); принятые по нему решения и оставшиеся в дорожной карте пункты —
в `docs/research/root-exit-node-design.json`.

Android отдаёт свой VPN-слот одному приложению за раз и никак не разбирает, что
при этом делает рутованное устройство ниже. `ip rule` просматривается по
возрастанию приоритета, и наши правила на 100 и 200 читаются раньше любого
правила, которое netd пишет для VPN-приложения (замер на телефоне автора:
priority 13000 и 16000–17000). Что бы мы ни забрали — мы забираем это первыми,
включая трафик, принадлежащий чужому туннелю.

Чего стоит «забрать слишком много», измерено с реальным клиентом (Exclave,
`com.github.dyhkwong.sagernet`, exit-нода выбрана с нашей стороны):

* Chrome, участник чужого туннеля, получал маршрут `dev tailscale0 table 52`.
  Его пакеты уходили в **нашу** exit-ноду, а его собственный клиент их не видел.
  Браузер погас.
* Каждый пакет на порт 53 переписывался в MagicDNS, включая запросы, которые
  системный резолвер делал от имени приложений того туннеля, — и приходили они,
  как описано в T3, с адресом источника чужого туннеля.

Поэтому у T2 и T3 один владелец на устройство, и начиная с 4.0.0 TailSocks их
отдаёт — целиком либо до той части устройства, которую чужой клиент не забрал.

#### Три состояния и переопределение

| Ситуация | Что установлено | Что работает |
|---|---|---|
| **TailSocks один** — VPN-слот никем не занят | T1 + T2 + T3 на всё устройство | Всё, ровно как раньше: exit-ноды, принятые subnet-маршруты, системный MagicDNS, исключения приложений. |
| **Устройством владеет другой клиент и забирает все приложения** | только T1 | Узел остаётся подключённым. Адреса tailnet доступны из любого приложения, имена MagicDNS разрешаются через публикацию в `/etc/hosts`, локальные SOCKS5/HTTP-прокси работают — и всё, что направлено в них, уходит через exit-ноду. **Не** работают: exit-нода и принятые subnet-маршруты для приложений, не направленных в эти прокси, и системный DNS. Чужой клиент сохраняет свои приложения и свой резолвер в целости. |
| **Устройством владеет другой клиент, но часть приложений он пропускает мимо себя** | T1 + T2, суженный до пропущенных uid'ов + T3 без сети этого клиента | Приложения, которые тот клиент отдал физической сети, идут через нашу exit-ноду и наши subnet-маршруты, а MagicDNS отвечает всему устройству — кроме запросов его собственного туннеля, которые остаются ему. Его участники не тронуты: их трафик остаётся в его туннеле, а имена им разрешает тот, на кого он их направил. |
| *(не состояние, а выход из двух предыдущих)* **включённое переопределение** | T1 + T2 + T3 на всё устройство | Наша сторона полна; чужой клиент теряет и трафик своих приложений, и разрешение имён на всё время работы TailSocks. |

Две средние строки — поведение по умолчанию, и ни одна из них не является
сбоем, поэтому приложение так и говорит, а не сообщает об ошибке — и говорит,
какая именно из двух, потому что предлагают они разное. При **полной уступке**
на главном экране вместо обычной строки Root написано **Только тейлнет**,
выбранная exit-нода показана как **не используется**, а не притворяется
работающей, и в настройках **Режим туннеля** и **DNS** есть пояснение, что
именно выключено и до каких пор. При **частичной уступке** не выключено ничего,
поэтому ничего такого и не написано: на главном экране — **Делим с другим VPN**,
строка exit-ноды остаётся активной с пометкой **Выходной узел: частично**, а
настройки говорят, для каких приложений уровни встали, а не от чего пришлось
отказаться. Экран Логи (вкладка ROOT) записывает, какие уровни встали и почему, а
**Проверить маршрутизацию** показывает тот же вердикт. Пустой priority 200 —
здоровое состояние при полной уступке; при частичной здоровым будет priority 200
с одним правилом на каждый переносимый диапазон uid'ов, а не одним на всё
устройство.

#### Частичная уступка: берём то, что чужой туннель пропускает мимо себя

VpnService, который туннелирует только часть приложений, остальные отдаёт
физической сети. Эти приложения ничьи: чужой клиент попросил их себе не
отдавать, и Android маршрутизирует их ровно так, как будто VPN нет вовсе.
Забрать их не стоит тому клиенту ничего, и это разница между телефоном, где
работает один туннель, и телефоном, где работают оба.

**Разрывы читаются из собственных правил netd, а не угадываются.** Членство в
VPN Android выражает диапазонами uid'ов, открытым текстом, и root-шелл их видит:

```
13000:	from all fwmark 0x0/0x20000 iif lo uidrange 0-10353 lookup tun0
13000:	from all fwmark 0x0/0x20000 iif lo uidrange 10355-10374 lookup tun0
13000:	from all fwmark 0x0/0x20000 iif lo uidrange 10376-99999 lookup tun0
```

Диапазоны — это участники; **разрывы между ними** — приложения, которые клиент
пропускает мимо себя (здесь uid 10354 — сам клиент — и 10375 — TailSocks).
Считаются только правила, чья таблица названа по интерфейсу чужого туннеля. Это
принципиально: *локальная* таблица физической сети (`wlan0_local`) содержит
`uidrange` на все uid'ы устройства, и если её учесть, разрывов не остаётся вовсе
— частичная уступка молча превращается обратно в полную.

На каждый уцелевший разрыв ставится своё правило catch-all — вместо одного
общего на всё устройство:

```
200: from all fwmark 0x0/0x2020000 iif lo uidrange 10380-10380 lookup 52
```

Селектор тот же, что и в общем правиле на всё устройство, но ограничен uid'ами, которые
чужому туннелю не нужны. В `ip rule` нет «кроме этих uid'ов», поэтому правил
столько же, сколько диапазонов, — ровно столько же ставит и сам чужой клиент.

**Два вида uid'ов не переносятся никогда**, и оба пришлось исключать вручную:

* **Собственный uid VPN-клиента.** Владелец VpnService всегда вне своего
  туннеля — иначе он зациклил бы через себя собственный трафик до релея, —
  поэтому его uid **всегда** оказывается в разрыве, независимо от того,
  пропускал ли его владелец хоть что-нибудь. Перенеся его, мы отправили бы
  соединение того клиента с его же релеем через нашу exit-ноду, чего никто не
  просил; кроме того, список разрывов тогда никогда не был бы пустым, и до
  полной уступки дело не дошло бы вовсе. Android знает, какие это приложения, и
  отвечает без root и без разрешений
  (`PackageManager.queryIntentServices(Intent("android.net.VpnService"))`), —
  поэтому мы спрашиваем его, а не гадаем.
* **uid'ы, за которыми не стоит ни одного приложения.** Android резервирует
  рядом с каждым приложением uid песочницы SDK (`appId + 10000`), так что в
  списке участников netd есть дырка и там. Замер на устройстве: uid 20354 лежал
  в разрыве, и за ним не стояло ни одного приложения — правило для него не
  могло совпасть ни с чем. Поэтому переносимое множество строится «от положительного»:
  *установленные* приложения, минус VPN-клиенты, минус мы сами, — а не
  вычитанием того, что выглядит подозрительно. Маленький разрыв (до 64 uid'ов —
  обычный случай, когда пользователь пропустил мимо туннеля несколько
  приложений) разбирается по одному uid'у; большой — клиент в режиме
  «туннелировать только эти приложения» оставляет снаружи почти всё устройство —
  сохраняется целиком, из него лишь вырезаются известные uid'ы VPN-клиентов:
  сотни правил по одному uid'у обходятся дороже, чем несколько правил, которые
  иногда ни с чем не совпадают.

Если после этого не остаётся ничего, частичной уступки нет: список разрывов пуст
и честно получается полная уступка — вторая строка таблицы.

**DNS делится по netId, а не по uid.** Собственное разрешение имён чужого
клиента должно остаться его собственным, и совпадение `-m owner --uid-owner`
этого сделать заведомо не может: на Android обычное приложение не отправляет
свои DNS-запросы само — оно вызывает `getaddrinfo`, а запрос отправляет
системный резолвер, от **своего** uid'а, не от uid'а приложения. Зато сохраняется
идентификатор сети netd: он проставляется в младшие 16 бит fwmark на пакете
резолвера. Замер за 18 секунд просмотра страницы внутри чужого туннеля, счётчики
в `mangle OUTPUT` по `udp --dport 53`:

| метка (маска `0x1ffff`) | пакетов | что это |
|---|---|---|
| `0x10084` | 6 | резолвер работает от имени приложения **внутри** чужого туннеля |
| `0x73` | 18 | разрешение имён по физической сети |

Поэтому в начало `TAILSOCKS_DNS`, раньше всего остального, ставится по одному
правилу на каждый чужой netId:

```
iptables -t nat -A TAILSOCKS_DNS -m mark --mark 0x84/0xffff -j RETURN
```

а всё остальное устройство остаётся на MagicDNS. netId'ы читаются той же пробой
`ip rule`, что и диапазоны uid'ов (`fwmark 0x10084/0x1ffff` → netId `0x84`), и
входят в то, что приложение сравнивает между тиками, — поэтому чужой туннель,
перезапустившийся с новым netId, замечается, и исключение переписывается.

**Чего частичная уступка не пытается делать.** Никто не пытается расширить маску
catch-all так, чтобы метка чужого туннеля из-под неё вышла: обычный трафик
приложений несёт netId 0 в метке, и это измерено напрямую —
`ip route get 1.1.1.1 mark 0x84 uid <приложение-участник>` по-прежнему отвечает
`dev tailscale0 table 52`. Никакая метка не переспорит правило, которое читается
раньше, — поэтому область и приходится задавать через uid'ы.

То, что **не** ставится, ещё и активно **снимается**: catch-all прошлой
установки (общий или суженный), `throw`-маршруты локальной сети,
которые мы писали в таблицу 52, изменённый `rp_filter`, правила исключений
приложений и оба DNS-хука убираются, когда уровень отдаётся; суженные правила
так же целиком переписываются, когда чужой туннель меняет состав пропускаемых
приложений. Пропущенная установка не убрала бы ничего, а эти правила вполне
могли остаться от предыдущей установки в этом же запуске.

Решение принимается заново при каждом изменении обстановки — чужой клиент
запустился или остановился, изменился состав его участников, поменялась
влияющая на выбор настройка, — а не один раз за запуск демона: ни уступка, ни
возврат устройства себе не ждут перезапуска.

#### Как распознаётся чужой клиент

Два независимых признака, потому что по отдельности ни одного не достаточно:

* **Ответ самого Android.** `ConnectivityManager` сообщает о сети с транспортом
  VPN. Но он сообщает только о том туннеле, участником которого является это
  приложение, — а клиент, исключивший TailSocks из своего туннеля (правильная
  настройка, см. ниже), для него невидим. Это ровно тот клиент, который мы и
  сломали бы.
* **Проба со стороны root.** Туннельный интерфейс, не наш (`tun*`, `ppp*`,
  `wg*`, `ipsec*`), **и** правила по uid'ам внутри собственной полосы
  приоритетов netd, указывающие на таблицу, которая не наша и не физическая.
  Эта пара — то, как netd выражает «эти приложения участники VPN», и больше
  никто на устройстве такого не пишет. Нужны обе половины: остановленный клиент
  оставляет за собой интерфейс, а вручную маршрутизируемый WireGuard не занимает
  VPN-слот.

Любого признака достаточно, чтобы уступить; безопасное направление — «устройство
принадлежит кому-то другому», и никогда наоборот. Проба со стороны root заодно
даёт и форму чужого туннеля — диапазоны uid'ов его участников и его netId'ы,
то есть всё, из чего собирается частичная уступка, — так что одно чтение
отвечает и на «есть ли здесь кто-то», и на «что он оставил». Диапазон, который
не разобрался, отбрасывается, а не додумывается: неверный отдал бы нам
собственные приложения того туннеля. Форму приложение запоминает и сверяет на
каждом тике обновления, потому что состав участников меняется и без падения
туннеля, а callback возможностей Android об этом сообщить не может (для
не-участника состав скрыт, а клиент, исключивший нас, — как раз тот, который нас
интересует). Вердикт, входные данные решения — метки, чужой туннель,
переопределение, диапазоны, разрывы, netId'ы — и причина пишутся в ROOT-лог при
каждой установке.

#### Переопределение

**Забрать устройство себе** (Настройки → Режим туннеля, рядом с остальными
переключателями Root-режима) ставит все три уровня на всё устройство независимо
ни от чего — без сужения и без исключения чужого DNS. По умолчанию выключено,
запоминается, и намеренно не переносится бэкапом профиля: это согласие насчёт
*этого* телефона и его второго клиента, а не настройка, которую стоит
восстанавливать где-то ещё. Диалог подтверждения называет цену, и ROOT-лог
повторяет её при каждой установке с этим флагом.

Включайте, когда чужой туннель не жалко прервать. Учтите при этом, что большая
часть того, от чего отказывается уступка — выход через exit-ноду и MagicDNS для
приложения, которому можно указать резолвер, — доступна через локальные прокси и
без отбирания устройства у кого бы то ни было; см. ниже.

#### При загрузке

Скрипт `service.d` выполняется на стадии `late_start`, задолго до старта службы
любого другого VPN-клиента, так что проверка здесь почти всегда отвечала бы
«устройство свободно», — а `PackageManager`а у него нет, поэтому даже при
правильном ответе он не смог бы поставить ни `throw`-маршруты локальной сети, ни
исключения приложений, ни исключения DNS по uid'ам. Поэтому он ставит T1 и на
этом останавливается (раздел 1). Всё решение целиком принимает приложение на
первом тике в состоянии `Running`, где уступка, её область и все смягчения
решаются в один приём.

**И честно о цене.** При выключенном переключателе «Работать в фоне» приложение
при загрузке не стартует вовсе, поэтому после перезагрузки на устройстве есть
только доступность tailnet: ни exit-ноды, ни принятых subnet-маршрутов для
остальных приложений, ни системного MagicDNS — пока вы не откроете TailSocks.
При включённом окно сужается до нескольких секунд между переходом демона в
`Running` и первой установкой правил приложением. До 4.0.0 загрузочный скрипт
ставил оба уровня для всего устройства сам, и окно было меньше, — но то, что он ставил, не
имело ни исключений для локальной сети, ни исключений приложений (перезагрузка с
выбранной exit-нодой уносила туда роутер, NAS и adb по Wi-Fi, а исключённые
приложения исключёнными не были) и вдобавок вообще не видело другого
VPN-клиента.

#### Что настроить в другом клиенте

Уступка не требует сотрудничества с той стороны. Но три настройки *его*
конфигурации определяют, насколько хорошо эти двое уживаются, и у реального
клиента — Exclave — первые две оказались верными без всякой ручной настройки.

1. **Исключить TailSocks из его туннеля** (per-app proxy в режиме bypass или его
   список исключённых приложений). Собственные сокеты демона несут бит protect
   от Android и в любом случае маршрутизируются физической сетью, так что
   туннель поднимется и без этого; но всё остальное — control plane через
   HTTP-прокси, обновления, Admin API — иначе поедет по второму туннелю без
   всякой на то причины, и сбой в том клиенте будет выглядеть как сбой
   TailSocks. Замер: диапазоны uid'ов Exclave уже пропускают и его собственный
   uid, и наш.
2. **Держать свои адреса вне диапазонов tailnet.** Наши правила priority 100
   забирают `100.64.0.0/10` и `fd7a:115c:a1e0::/48` для всех приложений на
   устройстве и отправляют их в `tailscale0`. Адрес его релея или сервера, его
   DNS-сервер и подсеть его собственного `tun`-интерфейса должны лежать вне обоих
   диапазонов. `100.64.0.0/10` — настоящее CGNAT-пространство, и некоторые
   клиенты выбирают адреса именно оттуда. Замер: Exclave маршрутизирует IPv4
   кусками по `/8`, но ставит `100.0.0.0/10` и `100.128.0.0/9` и намеренно не
   `100.64.0.0/10`, а его собственный туннель живёт на `172.19.0.0/30`.
3. **Направить его исходящий трафик в наш локальный прокси**, если ему нужен
   tailnet или exit-нода внутри собственного туннеля. SOCKS5-прокси (Настройки →
   Локальные прокси; по умолчанию `127.0.0.1:48115`, с паролем с того же экрана,
   если вы его задали) и HTTP-прокси обслуживает сам демон, поэтому всё, что
   идёт через них, следует за tailnet и выбранной exit-нодой независимо от того,
   какие уровни стоят на устройстве. Для имён MagicDNS внутри того клиента
   укажите ему наш локальный DNS-сервер, `127.0.0.1:1053`. Замер с выбранной
   exit-нодой: соединения через SOCKS5-прокси выходили через exit-ноду, и пир
   tailnet по нему отвечал.

Пункт 3 — причина, по которой «Root-режим или прокси-фронтенд» является ложным
выбором. Фронтенд, выбирающий upstream по приложению, может отправлять
выбранные вами приложения в TailSocks — с выходом через exit-ноду, — пока
устройство остаётся за ним и всё остальное продолжает работать.

### 6. Диагностика: «Проверить маршрутизацию» и вкладка ROOT в логах

* **Настройки → Диагностика и разработчик → Проверить маршрутизацию** показывает
  текущее состояние всего перечисленного: полные списки `ip rule` / `ip -6 rule`
  (правила приложения pref 100, исключения приложений pref 190, catch-all
  pref 200 и любые оставшиеся правила `52xx`), другие туннели на устройстве,
  таблицы 53, 1099 и 52, все маршруты через `tailscale0`, решение маршрутизации для
  `8.8.8.8` с меткой демона и без неё — по каждому исключённому uid'у и по
  первому исключённому локальному префиксу, `rp_filter` и сохранённое исходное
  значение, последний маркер запуска и строку `SO_MARK` из лога демона вместе с
  вердиктом приложения (почему pref 200 поставлен или нет), **вердикт
  соседства** — владеет ли устройством другой туннель, по чему он опознан и,
  если он пропускает часть приложений мимо себя, какие диапазоны uid'ов и какой
  netId переносятся, — обе цепочки со счётчиками пакетов на DNS-цепочке (это
  отличает «правила нет» от «правило есть и ни разу не сработало»), адрес
  `tailscale0` и версию `ip`.
* Каждый вызов root-шелла (установка/снятие маршрутизации, остановка демона,
  установка скриптов) логируется в категорию **ROOT**, у которой есть своя
  вкладка на экране **Логи**. Ошибки попадают туда, а не теряются молча.

### 7. Поведение при остановке: «Завершать Root-демон при остановке»

**Завершать Root-демон при остановке** (вкладка Root-режима, по умолчанию
включено) отправляет SIGTERM/SIGKILL root-процессу `libtailscale.so` при
нажатии Stop. Убивается только демон, запущенный для этого приложения — он
находится по аргументу `--socket=`, указывающему на приватный каталог данных
приложения, — поэтому второй профиль, `tailscaled` из Termux или другое
приложение с той же библиотекой никогда не пострадают.

Выключите переключатель, чтобы root-демон продолжал работать между остановками
приложения; приложение тогда просто отсоединяется. При следующем Start (или
изменении настроек, когда пользователь хочет соединение) оно подключается к
уже работающему демону вместо запуска нового. Ручная остановка окончательна в
любом случае: ничто не оживит службу, пока вы не запустите её снова.

## 📱 Включение Root-интеграции в Приложении

1. Откройте **TailSocks**.
2. Перейдите в **Настройки** → вкладка **Root-режим**.
3. **Предоставьте Root-права:** Нажмите для проверки наличия бинарника `su`.
4. **Установите Автозапуск Службы:** Включите переключатель установки `/data/adb/service.d/tailscaled.sh`.
5. **Установите Tailscale CLI:** Включите переключатель установки `/system/bin/tailscale` и оверлея Magisk.
6. Приложение отобразит текущий статус (установлено/не установлено), целевые пути и кнопки копирования путей.

## 💻 Примеры Использования CLI

После установки CLI-интеграции откройте любой root-терминал (`su` в Termux, ADB shell или серийную консоль) и выполняйте:

```bash
# Проверить статус узлов и подключенных пиров
su -c tailscale status

# Узнать IP-адреса Tailscale
su -c tailscale ip

# Выполнить ping до узла сети Tailnet
su -c tailscale ping <node-ip-or-name>

# Выполнить проверку сети и NAT traversal
su -c tailscale netcheck

# Узнать версию демона tailscaled
su -c tailscale version
```

### Полезные команды для диагностики:

```bash
# Просмотр логов tailscaled в реальном времени
su -c tail -f /data/data/io.github.bropines.tailscaled/logs/tailscaled.log

# Проверка работы процесса tailscaled от имени root
su -c ps -ef | grep tailscaled

# Проверка прав доступа к сокету
su -c ls -la /data/data/io.github.bropines.tailscaled/files/tailscaled.sock

# Правила, которыми владеет TailSocks (100: tailnet; 190: исключённые приложения;
# 200: catch-all exit-ноды — на всё устройство, когда VPN-слот свободен, по одному
# правилу на переносимый диапазон uid'ов при частичной уступке и ни одного при
# полной; правил 52xx быть не должно)
su -c ip rule show
su -c ip route show table 53
su -c iptables -t mangle -S TAILSOCKS_MARK
su -c iptables -t nat -S TAILSOCKS_DNS

# Таблица демона и решение по exit-ноде
su -c ip route show table 52                 # пиры, subnet-маршруты, 'default dev tailscale0' при exit-ноде
su -c ip route get 8.8.8.8                   # tailscale0 с exit-нодой, Wi-Fi/сотовая без неё
su -c ip route get 8.8.8.8 mark 0x2000000    # собственный путь демона: всегда физическая сеть
su -c grep -n 'TailSocks: daemon start' /data/data/io.github.bropines.tailscaled/logs/tailscaled.log | tail -n 1   # где начинается текущий запуск
su -c grep 'netns: SO_MARK' /data/data/io.github.bropines.tailscaled/logs/tailscaled.log   # ожидается после этой строки: '... set on tailscaled sockets (root bypass)'
```

### Диагностические скрипты (`tools/`)

Два скрипта в репозитории автоматизируют сбор данных для баг-репортов:

* **`tools/root-debug.sh`** — read-only снимок, запускается на устройстве от
  root. Печатает версию приложения, релевантные глобальные настройки, процесс
  демона и сокет, интерфейс `tailscale0` и другие туннели, policy-правила,
  таблицы 53 и 1099, решения маршрутизации с меткой и без, обе цепочки **со
  счётчиками пакетов** (это отличает «правила нет» от «правило есть, но трафик
  до него не доходит»), остатки старых правил, bind-mount `/system/etc/hosts`,
  пробу разрешения DNS и последние 40 строк лога демона. Ничего не изменяет.

  ```bash
  adb push tools/root-debug.sh /data/local/tmp/
  adb shell su -c sh /data/local/tmp/root-debug.sh          # необязательный аргумент: имя пакета
  ```

* **`tools/root-debug-session.sh <adb-serial> [package]`** — с хоста
  прогоняет полный цикл запуска/остановки через adb и сохраняет снимок на
  каждой фазе в `./root-debug-<timestamp>/`: `00-before.txt`,
  `01-t{5,15,30}s.txt` пока демон поднимается, `02-after.txt`,
  `03-after-stop.txt` (именно он показывает, остались ли правила после
  остановки), а также `logcat.txt` и внутренний лог приложения `applog.txt`.
  Служба запускается и останавливается через
  `am start-foreground-service … -a START_ACTION` / `-a STOP_ACTION`.

  ```bash
  tools/root-debug-session.sh 192.168.1.83:44895
  ```

Приложите полученный каталог (или одиночный снимок) к issue о Root-режиме.
