# Интеграция с Root и Системная Служба в TailSocks

TailSocks поддерживает расширенный **Root-режим** для Android-устройств с правами суперпользователя (**Magisk**, **KernelSU** или **APatch**). Root-режим позволяет демону `tailscaled` работать в качестве полноценного системного демона независимо от жизненного цикла Android UI, автоматически запускаться при загрузке устройства и предоставлять официальный консольный интерфейс `tailscale` CLI в терминальной среде.

---

## ⚡ Ключевая Архитектура и Возможности

### 1. Автозапуск Системной Службы через `service.d` (`tailscaled.sh`)
* **Путь:** `/data/adb/service.d/tailscaled.sh`
* **Запуск:** Выполняется автоматически Magisk / KernelSU / APatch на ранней стадии загрузки (`late_start` фаза) от имени `root` (UID 0).
* **Авто-определение Директории Состояния:** Динамически ищет существующие профили аккаунтов в `/data/data/io.github.bropines.tailscaled/files/states/` (по умолчанию `default` или `root`).
* **Управление Сокетом и Логами:** Использует сокет `/data/data/io.github.bropines.tailscaled/files/tailscaled.sock` с правами `0666` (благодаря встроенному патчу safesocket в ядре TailSocks). Логи демона (`tailscaled.log`) автоматически ротируются при превышении 2 МБ.
* **Передача Прокси и Control Plane:** Считывает переменные окружения из файла `/data/adb/tailsocks/control_proxy.env`, принадлежащего root (включая `ALL_PROXY`, `HTTP_PROXY`, `HTTPS_PROXY` и разрешённые IP через `TS_STATIC_HOSTS`). Приложение записывает его через `su` при каждом запуске root-демона; скрипт принимает только строки вида `export NAME='value'` и никогда не исполняет ничего из каталога данных приложения — туда может писать само приложение или восстановленный бэкап.
* **Маршрутизация при загрузке:** Как только появляется `tailscale0`, скрипт ставит те же правила, что и приложение (раздел 4 ниже): маскированный fwmark `0x1000000/0x1000000` → таблица `1099`, цепочки `TAILSOCKS_MARK` / `TAILSOCKS_DNS`, IPv4 и IPv6. DNS-редирект ставится только если ни `accept_dns`, ни `root_dns_redirect` не выставлены в `false` в `shared_prefs/tailsocks_global.xml`; остатки правил 3.5.x («голая» метка `1099`, прямые записи в `OUTPUT`) сначала удаляются. Приложение переустанавливает те же правила целиком при подключении к демону, а копия скрипта в `service.d` обновляется автоматически при обновлении приложения (раздел 3).

### 2. Интеграция с Tailscale CLI (`tailscale_cli.sh`)
* **Пути установки CLI-обёртки:**
  * `/data/adb/service.d/tailscale` (Исполняемый фаллбэк)
  * `/data/adb/modules/tailscaled/system/bin/tailscale` (Оверлей-модуль Magisk)
  * `/product/bin/tailscale` (Оверлей для раздела `/product/bin`)
  * `/system/bin/tailscale` (Прямая ссылка в `/system/bin`, если раздел доступен для записи)
* **Принцип работы:** Оборачивает нативный бинарник `libtailscale_cli.so` из установленного пакета приложения и автоматически подставляет аргумент `--socket=/data/data/io.github.bropines.tailscaled/files/tailscaled.sock` к каждой команде.
* **Применение:** Позволяет выполнять стандартные команды `tailscale` в Termux, `su`-шелле, ADB-шелле и скриптах.

### 3. Автоматическое Обновление при Обновлении Приложения (`BootReceiver`)
* **Отслеживаемые События:** `ACTION_BOOT_COMPLETED`, `QUICKBOOT_POWERON` и `ACTION_MY_PACKAGE_REPLACED`.
* **Логика Обновления:** При обновлении TailSocks (замене APK) `BootReceiver` автоматически обновляет скрипты службы `service.d` и CLI-обёртку из ассетов. Это гарантирует, что пути к нативным библиотекам `libtailscale.so` и `libtailscale_cli.so` в `/data/app/...` всегда актуальны и соответствуют новой версии без необходимости ручной переустановки.

### 4. Нативная маршрутизация TUN (`tailscale0`)

При включённом **Native Linux TUN** демон создаёт настоящий интерфейс ядра
`tailscale0`, оставляя слот Android VPN свободным. TailSocks настраивает
policy-routing вокруг него после перехода демона в состояние `Running`:

* **Таблица `1099`** содержит маршрут `100.64.0.0/10` (и `fd7a:115c:a1e0::/48`)
  через `tailscale0`. Трафик направляется в неё двумя правилами с priority 100:
  `ip rule … fwmark 0x1000000/0x1000000 table 1099` для помеченных пакетов и
  `ip rule … to 100.64.0.0/10 table 1099` (и IPv6-диапазон) по адресу назначения.
  Второе нужно для собственных сокетов демона: метка ставится в `mangle OUTPUT`
  *после* того, как ядро уже выбрало source-адрес из таблицы Wi-Fi, так что без
  него запросы демона к split-DNS-резолверу на пире уходили в `tailscale0` с
  Wi-Fi-адресом источника и не получали ответа.
* **`TAILSOCKS_MARK`** (mangle, вызывается из `OUTPUT` для диапазонов tailnet)
  ставит эту метку через `--set-xmark 0x1000000/0x1000000`. Через маску
  трогается лишь один старший бит: Android хранит в fwmark собственное решение
  о маршрутизации (netId в младших 16 битах, выше — флаги explicit/protect/
  permission), и «голый» `--set-mark 1099`, использовавшийся до 4.0.0, затирал
  его целиком, ломая маршрутизацию, когда сетью по умолчанию владел другой VPN.
  Старая метка и старые правила без цепочек удаляются автоматически при первом
  запуске после обновления.
* **`TAILSOCKS_DNS`** (nat, вызывается из `OUTPUT` для порта 53 UDP/TCP)
  перенаправляет системный DNS на MagicDNS (`100.100.100.100`). Два класса
  трафика исключаются до редиректа, в этом порядке:
  * диапазон tailnet `100.64.0.0/10` — чтобы Split DNS-резолверы на пирах
    оставались доступны напрямую;
  * собственные upstream-резолверы демона (`TS_DNS_FALLBACK`, берутся из
    настройки DNS fallback). Без этого запросы самого резолвера
    перенаправляются обратно в него же, и ни одно внешнее имя не резолвится.

  Редирект ставится **только** при включённом `accept-dns` (перенаправлять всё
  устройство на резолвер, который не отвечает, значит сломать DNS целиком) и
  отключается независимо переключателем **Системный DNS через MagicDNS**
  (вкладка Root-режима) — это выход, когда системный резолвер должен остаться
  за другим VPN или DNS-фильтром.
* **Exit-ноды, subnet-маршруты и таблица `52`.** Всё, что знает только демон,
  он пишет в собственную таблицу `52`: `/32` пиров, принятые subnet-маршруты,
  `100.100.100.100/32`, `default dev tailscale0` пока выбрана exit-нода и
  `throw`-маршруты для префиксов локальной сети при включённом *allow LAN
  access*. Приложение в эту таблицу не пишет, не очищает и не проверяет её —
  оно лишь добавляет одно постоянное правило рядом с правилами priority 100:

  ```
  200: from all fwmark 0x0/0x2020000 iif lo lookup 52
  ```

  Каждый непомеченный локально сгенерированный пакет сначала смотрит в таблицу
  52 и, если совпадения нет, проваливается в собственные правила Android (10000
  и выше). Поэтому включение и выключение exit-ноды целиком обрабатывает
  `router.Set()` демона, как на десктопном Linux: в приложении нет состояния
  exit-ноды и нечего переделывать при переходе Wi-Fi ↔ сотовая сеть. Безопасным
  это правило делают две вещи:

  * **Демон помечает собственные сокеты.** Каждый сокет, который tailscaled
    открывает сам (WireGuard/disco UDP, DERP, control plane, STUN, DNS
    fallback), несёт `SO_MARK 0x2000000` (бит 25, патч 16 — вне собственных
    бит fwmark Android 0–20 и отдельно от бита 24 приложения). Такие пакеты
    пропускают pref 200 и уходят в физическую сеть по правилам netd. Без метки
    default-маршрут таблицы 52 заглотил бы собственные пакеты туннеля и
    зациклил всё устройство — поэтому TailSocks ставит pref 200 **только
    после** того, как текущий запуск демона записал в лог `netns: SO_MARK
    0x2000000 set on tailscaled sockets` (одной непрерывной строкой; перед ней
    стоят префикс Go с датой и временем `YYYY/MM/DD HH:MM:SS` и префикс
    компонента, например `magicsock:`). Демон дописывает в один и тот же файл
    от запуска к запуску и в этой сборке не печатает собственного стартового
    баннера (`ts_omit_logtail`), поэтому «текущий запуск» — это всё после
    более поздней из двух строк: `TailSocks: daemon start`, которую оба способа
    запуска — загрузочный скрипт и приложение — пишут непосредственно перед
    стартом демона, и собственной строки демона
    `wgengine.NewUserspaceEngine(tun "tailscale0") ...`, которую любое ядро
    печатает при каждом старте прямо перед созданием движка (а вместе с ним и
    пробы). Лог просматривается с конца до этого начала запуска, сколько бы
    демон ни проработал, и строка пробы засчитывается, только если ниже неё
    найдено начало запуска — так что ни строка прежнего запуска, ни демон,
    перезапущенный вручную, не могут позаимствовать чужой вердикт; лог вообще
    без начала запуска считается непроверенным, и pref 200 не ставится. Во
    всех отрицательных
    случаях в ROOT-логе появляется `exit node unavailable: daemon does not mark
    sockets (<причина>)`, и на pref 200 ничего не ставится; маршрутизация
    tailnet через таблицу 1099 от этого не зависит. Загрузочный скрипт ждёт ту
    же строку в части лога своего запуска до 20 с, прежде чем добавить правило;
    строки с пометкой `TailSocks:` пишут приложение и сам скрипт — они не
    учитываются.
  * **Маска учитывает бит `protectedFromVpn` Android** (`0x20000`) — тот же
    приём, что netd использует в собственных VPN-правилах: сокеты, которые
    Android намеренно держит вне VPN (проверки доступности сети, MMS/IMS,
    защищённые сокеты других VPN-приложений), тоже минуют exit-ноду. `iif lo`
    ограничивает правило исходящими lookup'ами, так что клиенты точки доступа
    остаются на правилах netd.

  Ответы на помеченные сокеты демона приходят по Wi-Fi/сотовой сети и проходят
  reverse-path-проверку с меткой 0, которая теперь через таблицу 52 указывает
  на `tailscale0`, — строгий `rp_filter` (1) отбросил бы их. Поэтому, если хоть
  один интерфейс в строгом режиме, `all` переводится в loose (2), прежнее
  значение сохраняется в `/data/adb/tailsocks/rp_filter.orig` и
  восстанавливается при очистке. Правило перечитывается после установки
  (бинарь `ip`, потерявший маску, оставил бы правило «совпадает со всем» — оно
  удаляется и о нём сообщается), а десктопные правила, оставшиеся от ядра до
  4.0 (`5210 lookup main`, `5230 lookup default`, `5250 unreachable`, `5270
  lookup 52`), удаляются по содержимому при каждой установке и при очистке.

  На Android роутер демона делает только то, что может только он: поднимает
  интерфейс, ставит адреса, пишет маршруты в таблицу 52. Он не ставит
  ip-правила `52xx` (таблицы `main`/`default` на Android пусты, так что
  десктопные правила либо зацикливают, либо роняют трафик) и вообще не трогает
  netfilter — метки Tailscale `0x40000`/`0x80000` совпадают с битами
  разрешений netd, а на части ядер отсутствует тип nft-цепочки `nat`; отсюда и
  брался прежний health-warning `router config failed`. Root-режим — только
  клиент: в нём это устройство не может быть exit-нодой или subnet-роутером.

* **`TAILSOCKS_BYPASS`** (mangle, вызывается из `OUTPUT` без собственного
  условия) — исключение отдельных приложений. Root-режим по своей природе
  действует на всё устройство: DNS-редирект выше ловит порт 53 любого
  приложения, а catch-all с приоритетом 200 отправляет в exit-ноду каждый
  непомеченный локальный пакет. Поэтому приложения из списка
  **Настройки → Режим туннеля → Исключенные приложения** (тот же список, что
  TUN-режим отдаёт в `addDisallowedApplication`: один список на оба режима
  туннеля) при каждой установке правил превращаются в uid'ы и исключаются
  дважды:

  ```
  iptables -t nat    -A TAILSOCKS_DNS    -m owner --uid-owner 10234 -j RETURN
  iptables -t mangle -A TAILSOCKS_BYPASS -m owner --uid-owner 10234 -j MARK --set-xmark 0x2000000/0x2000000
  ```

  `RETURN` ставится в начало `TAILSOCKS_DNS`, до правил DNAT, так что у этого
  приложения остаётся системный резолвер даже когда MagicDNS нездоров: exit-нода,
  отвечающая `403`, раньше уносила с собой разрешение имён на всём устройстве.
  Метка — тот самый bypass-бит демона, который маска правила с приоритетом 200
  уже исключает, поэтому трафик приложения уходит через физический интерфейс, а
  не через exit-ноду. Оба правила ставятся для IPv4 и IPv6 (DNS-правило — только
  IPv4, потому что редирект тоже только IPv4).

  Что **не** исключается: правила приоритета 100 этот бит не смотрят, поэтому
  исключённое приложение по-прежнему достаёт адреса тейлнета через
  `tailscale0` — наружу возвращаются только его DNS и маршрут по умолчанию.
  Имена MagicDNS для него разрешаются лишь через публикацию в `/etc/hosts`, а
  домены split-DNS не разрешаются вовсе.

  Пакет, которого уже нет на устройстве, пропускается и называется в ROOT-логе.
  `-m owner` — необязательный модуль ядра (`xt_owner`): если его нет, правила
  отклоняются, в ROOT-лог пишется `per-app exclusions NOT applied: this kernel
  has no iptables -m owner match`, а все остальные правила ставятся как обычно —
  Root-режим просто остаётся общесистемным. При пустом списке не генерируется
  вообще ничего, и набор правил побайтово совпадает с прежними версиями.
  Цепочка снимается при очистке вместе с остальными.

Все правила живут в именованных цепочках — они идемпотентны, их видно через
`iptables -t nat -S TAILSOCKS_DNS` / `iptables -t mangle -S TAILSOCKS_MARK` /
`iptables -t mangle -S TAILSOCKS_BYPASS`,
при каждом запуске они заменяются как единое целое и снимаются одним махом при
остановке службы. Скрипт проверяет собственный результат (таблица заполнена,
DNS-цепочка существует), а не доверяет коду возврата шелла; после трёх
неудачных попыток он сдаётся и сообщает об этом в лог.

### 5. Диагностика: «Проверить маршрутизацию» и вкладка ROOT в логах

* **Настройки → Root-режим → Проверить маршрутизацию** показывает текущее
  состояние всего перечисленного: полные списки `ip rule` / `ip -6 rule`
  (правила приложения pref 100, catch-all pref 200 и любые оставшиеся правила
  `52xx`), другие туннели на устройстве, таблицы 1099 и 52, все маршруты через
  `tailscale0`, решение маршрутизации для `8.8.8.8` с меткой демона и без неё,
  `rp_filter`, последний маркер запуска и строку `SO_MARK` из лога демона
  вместе с вердиктом приложения (почему pref 200 поставлен или нет), обе
  цепочки, адрес `tailscale0` и версию `ip`.
* Каждый вызов root-шелла (установка/снятие маршрутизации, остановка демона,
  установка скриптов) логируется в категорию **ROOT**, у которой есть своя
  вкладка на экране **Логи**. Ошибки попадают туда, а не теряются молча.

### 6. Поведение при остановке: «Завершать Root-демон при остановке»

**Завершать Root-демон при остановке** (вкладка Root-режима, по умолчанию
включено) отправляет SIGTERM/SIGKILL root-процессу `libtailscale.so` при
нажатии Stop. Убивается только демон, запущенный для этого приложения — он
находится по аргументу `--socket=`, указывающему на приватный каталог данных
приложения, — поэтому второй профиль, `tailscaled` из Termux или другое
приложение с той же библиотекой никогда не пострадают.

Выключите переключатель, чтобы root-демон продолжал работать между остановками
приложения; приложение тогда просто отсоединяется. При следующем Start (или
изменении настроек, когда пользователь хочет соединение) оно подключается к
уже работающему демону вместо запуска нового. Ручная остановка окончательна в
любом случае: ничто не оживит службу, пока вы не запустите её снова.

## 📱 Включение Root-интеграции в Приложении

1. Откройте **TailSocks**.
2. Перейдите в **Настройки** → вкладка **Root-режим**.
3. **Предоставьте Root-права:** Нажмите для проверки наличия бинарника `su`.
4. **Установите Автозапуск Службы:** Включите переключатель установки `/data/adb/service.d/tailscaled.sh`.
5. **Установите Tailscale CLI:** Включите переключатель установки `/system/bin/tailscale` и оверлея Magisk.
6. Приложение отобразит текущий статус (установлено/не установлено), целевые пути и кнопки копирования путей.

## 💻 Примеры Использования CLI

После установки CLI-интеграции откройте любой root-терминал (`su` в Termux, ADB shell или серийную консоль) и выполняйте:

```bash
# Проверить статус узлов и подключенных пиров
su -c tailscale status

# Узнать IP-адреса Tailscale
su -c tailscale ip

# Выполнить ping до узла сети Tailnet
su -c tailscale ping <node-ip-or-name>

# Выполнить проверку сети и NAT traversal
su -c tailscale netcheck

# Узнать версию демона tailscaled
su -c tailscale version
```

```bash
# Просмотр логов tailscaled в реальном времени
```

### Диагностические скрипты (`tools/`)

Два скрипта в репозитории автоматизируют сбор данных для баг-репортов:

* **`tools/root-debug.sh`** — read-only снимок, запускается на устройстве от
  root. Печатает версию приложения, релевантные глобальные настройки, процесс
  демона и сокет, интерфейс `tailscale0` и другие туннели, policy-правила,
  таблицу 1099, решения маршрутизации с меткой и без, обе цепочки **со
  счётчиками пакетов** (это отличает «правила нет» от «правило есть, но трафик
  до него не доходит»), остатки старых правил, bind-mount `/system/etc/hosts`,
  пробу разрешения DNS и последние 40 строк лога демона. Ничего не изменяет.

  ```bash
  adb push tools/root-debug.sh /data/local/tmp/
  adb shell su -c sh /data/local/tmp/root-debug.sh          # необязательный аргумент: имя пакета
  ```

* **`tools/root-debug-session.sh <adb-serial> [package]`** — с хоста
  прогоняет полный цикл запуска/остановки через adb и сохраняет снимок на
  каждой фазе в `./root-debug-<timestamp>/`: `00-before.txt`,
  `01-t{5,15,30}s.txt` пока демон поднимается, `02-after.txt`,
  `03-after-stop.txt` (именно он показывает, остались ли правила после
  остановки), а также `logcat.txt` и внутренний лог приложения `applog.txt`.
  Служба запускается и останавливается через
  `am start-foreground-service … -a START_ACTION` / `-a STOP_ACTION`.

  ```bash
  tools/root-debug-session.sh 192.168.1.83:44895
  ```
