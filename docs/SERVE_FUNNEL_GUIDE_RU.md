# Руководство по Tailscale Serve, Funnel & Services в TailSocks

*Примечание: Начиная с версии v2.0-beta, интерфейс Serve был полностью обновлен — добавлен чиповый интерфейс и двухэтапная синхронизация через LocalAPI для максимальной надежности.*

TailSocks позволяет пробрасывать локальные сервисы в вашу сеть Tailnet (Serve) или в публичный интернет (Funnel), используя сетевой движок Tailscale в пользовательском пространстве (userspace). Поскольку TailSocks работает без системного VPN TUN-интерфейса, эти функции служат основным средством обеспечения доступа к локальным ресурсам.

---

## 1. Tailscale Serve (Внутренний доступ)
Serve делает локальный порт доступным для других устройств в вашей сети Tailnet под DNS-именем вашего устройства (например, `my-phone.tailnet-1234.ts.net`).

### Типы обработчиков (Handler Types):
* **Proxy (Прокси):** Перенаправляет трафик на локальный адрес (например, `127.0.0.1:8080`). Это наиболее частый сценарий для веб-приложений.
* **Path (Статический каталог):** Раздает файлы из указанного каталога на вашем Android-устройстве. *Примечание: Убедитесь, что TailSocks имеет разрешение «Доступ ко всем файлам».*
* **Text (Текст):** Напрямую выдает текстовую или HTML-строку. Удобно для простых страниц статуса или отладки.
* **Redirect (Перенаправление):** Отправляет HTTP 302/301 редирект на другой URL. Поддерживает переменные, такие как `${HOST}` и `${REQUEST_URI}`.

### Варианты протоколов:
* **Web (HTTPS/HTTP):** Tailscale автоматически управляет TLS-сертификатами для HTTPS.
* **TCP Forward (Проброс TCP):** Прямой проброс байтового потока.
    * **Terminate TLS:** Tailscale расшифровывает соединение перед отправкой на локальный целевой порт.
    * **Proxy Protocol:** Отправляет заголовок [PROXY protocol](https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt) (v1 или v2) на целевой порт, сохраняя исходный IP-адрес клиента.

## 2. Tailscale Funnel (Публичный доступ)
Funnel расширяет возможности Serve, разрешая доступ к вашему устройству из **публичного интернета**.

### Требования:
1. **Включенный HTTPS:** В вашей сети Tailnet должны быть включены MagicDNS и HTTPS.
2. **Права в ACL:** В политике сети (tailnet policy) должно быть разрешено право `funnel`.
3. **Ограниченные порты:** Funnel работает только на определенных портах: `443`, `8443` и `10000`.

### Пример настройки ACL:
Добавьте следующий фрагмент в политику сети через консоль администратора Tailscale:
```json
"nodeAttrs": [
    {
        "target": ["tag:server", "my-phone@example.com"],
        "attr": ["funnel"]
    }
]
```

## 3. Виртуальные Сервисы Tailscale (`svc:`)
Виртуальные сервисы позволяют размещать службы под **отдельным доменным именем**, отличным от имени вашего устройства. Например, устройство `my-phone` может хостить сервис по адресу `webapp.tailnet-1234.ts.net`.

### Особенности и ограничения:
* **Независимое доменное имя:** Доступно по адресу `https://service-name.tailnet.ts.net`.
* **Сначала создать, потом подтвердить:** определите службу в консоли администратора Tailscale (страница **Services**) до того, как этот узел её объявит, а после объявления подтвердите узел как её хост там же. Либо доверьте это политике через `autoApprovers.services`. Пока не сделано и то и другое, tailnet по имени службы не отвечает.
* **Без поддержки L3 TUN режима:** Поскольку TailSocks работает в режиме userspace-networking без VpnService, режим L3 Tun (перенаправление всего трафика на виртуальный IP) **не поддерживается**. Поддерживается только использование Serve/Funnel на конкретных портах.
* **Требования к ACL:** При использовании расширенных политик требуется определение `tag` или `service` в ваших ACL.

## 🛠 Использование Serve & Funnel в TailSocks

Экран открывается карточкой этого узла: адрес, может ли он получить HTTPS-сертификат,
разрешён ли Funnel и на каких портах, может ли он хостить службы (узел с тегами). Ниже
один список правил. Карточка показывает адрес, по которому правило доступно, что оно
делает, метку **Публично** (Funnel) или **Tailnet**, и отвечает ли что-нибудь на его цели.

1.  Нажмите **+**.
2.  Выберите, что открыть: **локальный сервис** (HTTP-прокси), **текст**, **редирект** или сырой **TCP-порт**.
3.  Укажите цель и порт на этом узле, можно несколько (`443, 2550`, для демона это отдельные записи); 443, 8443 и 10000 (порты Funnel) подставляются одним нажатием.
4.  Включите **Интернет (Funnel)**, если правило должно быть доступно снаружи. Когда переключатель включить нельзя, он объясняет почему: нет возможности Funnel, порт не из разрешённых, обычный HTTP или служба.
5.  Для нового правила выберите область: **это устройство** или **служба** (`svc:имя`, только узлы с тегами). После сохранения приложение предложит определить службу в tailnet и подтвердить этот узел как её хост через Admin API (нужна настройка в Настройки → Admin API; сначала спросит отпечаток); без API оба шага делаются в консоли администратора. То же действие есть в меню карточки: **Опубликовать в tailnet**.
6.  В **Дополнительно** живут термины демона: путь монтирования (несколько обработчиков на одном порту), обычный HTTP вместо HTTPS, бэкенд с самоподписанным сертификатом (`https+insecure://`), терминация TLS и протокол PROXY для TCP.
7.  Нажмите **Добавить**. Меню карточки: изменить, скопировать ссылку, приостановить (правило уходит из демона, но остаётся в списке до возобновления), удалить; меню экрана: экспорт HTTPS-сертификата и удаление всех правил.

### Переменные в Редиректах:
* `https://example.com/${REQUEST_URI}`: Перенаправляет пользователя со сохранением пути.
* `301:https://newsite.com`: Постоянное перенаправление (Permanent redirect).

### PROXY Protocol:
* **v1:** Текстовый заголовок в человекочитаемом формате (например, `PROXY TCP4 1.2.3.4 ...`).
* **v2:** Бинарный заголовок (более эффективный).
Используйте этот режим, если ваш бэкенд-сервер (Nginx, Go и т. д.) поддерживает и ожидает заголовки PROXY protocol.
