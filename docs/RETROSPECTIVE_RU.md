# Эволюция проекта и Архитектурная ретроспектива

В данном документе описан путь развития проекта TailSocks — от ранних Proof-of-Concept (PoC) итераций до текущей стабильной архитектуры, с разбором уроков, извлеченных из первоначальных проектных допущений.

---

## Этап 1: Бессрочный прокси (Stateless Proxy, ранние v1.x)
Первоначальная цель заключалась в том, чтобы проверить, может ли демон Tailscale работать как Position Independent Executable (PIE) бинарник на платформе Android. На этом этапе аутентификация выполнялась вручную через консоль CLI, а приложение функционировало как статический SOCKS5-клиент.

---

## Этап 2: Активное управление (Модель «Агрессивного опроса»)
По мере интеграции функций аутентификации и динамических настроек мы исходили из предположения, что демон может терять свое внутреннее состояние из-за агрессивных механизмов энергосбережения Android и переключения сетевых интерфейсов.

**Выбранный архитектурный подход:**
Чтобы гарантировать синхронизацию, в приложение был встроен цикл «активного управления» (Active Management loop). Этот цикл каждые 10–15 секунд принудительно вызывал `tailscale up` с полным набором параметров, чтобы с силой «привести» демон в соответствие со состоянием интерфейса.

**Выявленные проблемы:**
Данный подход вызвал критическую нестабильность системы:
* **Циклы аутентификации:** Постоянное повторное внедрение параметров приводило к сбросу сессий и частым ошибкам `410 Gone`.
* **Нарушение P2P-соединений:** Частые обновления конфигурации сбрасывали движок `magicsock`, препятствуя установке прямых соединений между узлами через NAT.
* **Избыточная сложность:** Потребовалось огромное количество вспомогательной логики (хрупкие задержки, обработчики Broadcast Receiver) для борьбы с побочными эффектами постоянного опроса.

---

## Этап 3: Архитектура пассивного моста (Текущая модель)
Мы пришли к выводу, что демон Tailscale сам по себе является самодостаточным конечным автоматом, эффективно управляющим собственным жизненным циклом и восстановлением сети. Архитектура была переведена на пассивную модель.

**Ключевые улучшения:**
1. **Инициализация без сохранения состояния:** Полный набор флагов конфигурации передается только при первичном запуске или явном изменении настроек пользователем.
2. **Мониторинг через Watchdog:** UI отслеживает состояние демона с помощью неинвазивных запросов статуса и контроля процесса (watchdog), избегая прямого вмешательства в его работу.
3. **Приоритет изоляции:** Стабильность достигается за счет чистой изоляции файловой системы (уникальные пути хранения состояния для каждого аккаунта), а не постоянного вмешательства.

## Обновление (2026-05-06): Полный переход на Local API и поддержка Serve/Funnel
Проект достиг 100% независимости от вызовов CLI-бинарников для управления жизненным циклом.
- **Прорыв с ETag:** Было обнаружено, что API `ServeConfig` в Tailscale требует строгой синхронизации ETag через заголовки `If-Match`. Отсутствие актуального ETag приводит к персистентным ошибкам 500. Проблема была решена встраиванием автоматического извлечения ETag в Go HTTP-транспорт.
- **Виртуальные сервисы (Virtual Services):** Успешно реализована поддержка Tailscale Services, позволяющая Android-клиенту выступать в роли хоста для именованных виртуальных узлов (`svc:*`). Это доказывает, что Android PIE демон способен полностью выполнять функции L7-сервисов.
- **Ограничения прокси на Android:** Подтверждено наличие глубоко вшитых ограничений в сетевом стеке Tailscale для Android относительно исходящих SOCKS5-прокси. Даже с патчами `netns` и хуками `SetProxyFunc` демон предпочитает нативные HTTP-прокси.
- **Максимизация шины событий (Event Bus):** Переход на Mask `4095` устранил все проблемы с «зависшим состоянием» в UI, так как приложение теперь получает мгновенные дельта-обновления NetMap и списка узлов.

---

## Обновление (2026-05-28): Taildrive в режим Userspace-Networking и маршрутизация Netstack
Мы успешно реализовали высокопроизводительную интеграцию Taildrive (WebDAV) для просмотра и открытия файлов как на локальном устройстве, так и на удаленных узлах без использования системного `VpnService` (в режиме без VPN).
- **Преодоление барьера FakeTUN Loopback:** В режиме userspace пакеты, адресованные самому себе на `100.100.100.100:8080` (виртуальный сервис WebDAV), отбрасывались устройством Fake TUN. Мы обошли это, реализовав перехват и loopback-маршрутизацию в `netstack.go` (`inject`), доставляя loopback-пакеты напрямую через `DeliverLoopback`.
- **Маршрутизация удаленного диалера (Peer Dialer):** Просмотр удаленных ресурсов требует, чтобы локальный файловый менеджер запрашивал эндпоинт peerapi удаленного узла (например, `100.x.y.z:37350`). Поскольку стандартные сетевые сокеты не могут достичь сети Tailnet без системного VPN, мы направили запросы к узлам в `driveimpl` через `tsdial.Dialer.UserDial`, изолировав локальный loopback-трафик (`127.0.0.1`) на стандартном диалере для предотвращения сбоев пространств имен (`netns`) на Android.
- **Исправление выбора исходного IP в Netstack:** Было замечено, что gVisor netstack при инициации исходящих P2P-соединений без явного привязки сокета выбирал IP виртуального сервиса `100.100.100.100` в качестве IP-адреса источника вместо зарегистрированного IP-адреса Tailscale данного узла. Это приводило к тому, что WireGuard немедленно отбрасывал исходящие пакеты. Мы исправили это, модифицировав `DialContextTCP` и `DialContextUDP` в `netstack.go` для автоматического поиска локального IP-адреса Tailscale и явной привязки исходящего сокета к нему.

## Заключение
Отказ от "активной" PoC-модели в пользу профессионального пассивного моста, переход на архитектуру Local API и устранение аномалий маршрутизации на уровне netstack позволили создать самую стабильную и функциональную сборку TailSocks на сегодняшний день.

---

## Приложение: Ключевые исследования и отладка
* **Удержание HTTP Redirect в Serve:** Выявлено, что установка обработчиков HTTP Redirect через LocalAPI требует строгой валидации. Демон отклоняет URL перенаправления без указания схемы (`https://` теперь подставляется автоматически). Кроме того, отправка конфликтующих булевых флагов (например, `HTTPS: true` и `HTTP: false`) вызывала скрытый сброс конфигурации. Модели Kotlin были скорректированы для полного исключения неактивных флагов из запроса.
* **Экспорт SOCKS5 и SagerNet:** Для бесшовной интеграции с прокси-клиентами (такими как SagerNet/v2rayNG) TailSocks динамически генерирует стандартизированные URI-схемы `socks5://`, содержащие учетные данные аутентификации, внедряемые при запуске демона через `TS_SOCKS5_USER` и `TS_SOCKS5_PASS`.
* **Привязка и маршрутизация WebDAV в Userspace:** Обнаружено, что netstack от gVisor позволяет назначать несколько IP-адресов на один сетевой интерфейс (NIC). При выполнении исходящих соединений по умолчанию выбирается первый доступный или недавний адрес без учета карт маршрутизации координатора. Путем введения строгих ограничений `DialContextTCPWithBind` в `netstack.go` мы обеспечили полное соответствие правилам маршрутизации, достигнув передачи данных без потери пакетов через каналы WireGuard в режиме userspace.
