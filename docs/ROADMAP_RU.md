# План Развития Проекта (Roadmap)

Этот документ описывает планируемые функции, архитектурные улучшения и цели рефакторинга проекта TailSocks.

---

## ✅ Завершённые Этапы
- [x] **Стабильность ядра:** Пассивное управление демоном и декларативная конфигурация.
- [x] **Передача файлов:** Реализация Taildrop с интеграцией в Storage Access Framework.
- [x] **Изоляция профилей:** Мультиаккаунтная система с независимыми каталогами состояния.
- [x] **Сетевые возможности:** Кастомное DNS-обертывание и поддержка Exit Nodes.
- [x] **Tailscale Serve/Funnel:** Нативный UI для хостинга сервисов и публичного доступа.
- [x] **Local API v0:** Управление 100% без CLI через Go-HTTP мост.
- [x] **Интеграция с системой:** Базовая плитка Быстрых настроек (Quick Settings Tile) для переключения подключения.
- [x] **Мониторинг сервисов:** Проверки состояния (health checks) и логи запросов для размещенных сервисов Serve/Funnel.
- [x] **Поиск и фильтрация:** Функция поиска в списке узлов (Peers) и логах.
- [x] **Защита от энергосбережения:** Диалог помощи пользователю по выходу из ограничений батареи.
- [x] **Переключение аккаунтов в плитах:** Расширение плитки Быстрых настроек для переключения между профилями.
- [x] **Прокси панели управления:** Поддержка SOCKS5/HTTP прокси для трафика управления с атомарными патчами и фиксом обхода netns.
- [x] **Зашифрованные бэкапы:** Ручной бэкап состояния приложения, зашифрованный пользовательским паролем (AES-GCM) для защиты ключей узлов.
- [x] **Плитки Быстрых Настроек:** Плитки в шторке Android для управления переключением профилей и состояния подключения.
- [x] **R8-минификация (4.0.0):** `isMinifyEnabled`/`isShrinkResources` включены для релизных сборок. Gson заменён на `kotlinx.serialization`, сервис AppFunctions создаёт сгенерированные KSP реестры напрямую, а Gradle-задача `verifyReleaseNativeMethods` роняет сборку, если R8 удалил JNI-метод.
- [x] **Ужесточение Root-режима (4.0.0):** отдельные цепочки `TAILSOCKS_MARK`/`TAILSOCKS_DNS`, fwmark с маской `0x1000000/0x1000000`, диагностика «Проверить маршрутизацию» и вкладка ROOT в логах.
- [x] **Безопасность автоматизации (4.0.0):** broadcast receiver требует секретный токен; AppFunctions (Gemini, Android 16+) реально выполняются и подчиняются переключателю автоматизации.
- [x] **Доступ из LAN, автопереподключение, восстановление службы в фоне и версионированные бэкапы (4.0.0).**
- [x] **Сосуществование Root-режима с другими VPN (4.0.0):** набор правил разделён на уровни — доступность тайлнета, перехват маршрута по умолчанию, общесистемный редирект DNS, — причём у последних двух на устройстве только один владелец. Появилась частичная уступка: мы берём ровно те uid, которые чужой клиент вывел из своего туннеля, редирект DNS включается только пока MagicDNS отвечает, а интерфейсы с адресом внутри 100.64.0.0/10 больше не захватываются. Проверено на Redmi автора (APatch), в том числе после настоящей перезагрузки.
- [x] **Сообщать настоящую ОС (4.1.1):** выбор на уровне профиля, делается при его создании (онбординг, диалог добавления аккаунта; переключатель в Настройках — для профиля, который ещё не вошёл, иначе предлагается новый профиль). Выключено — маскировка патча 06: OS `linux`, App `tailscale-cli`, DeviceModel `Tailsocks`. Включено — узел регистрируется как OS `android` с настоящей моделью, версией Android и источником установки, как официальный клиент. Измерено 2026-09-07: такой узел получает `https`/`funnel`, сертификаты и рабочий Funnel; координатор отвергает только узел, сменивший ОС после регистрации.
- [x] **Root-режим после перезагрузки (4.1.1):** загрузочный скрипт теперь берёт каталог состояния активного профиля, адреса прослушивания SOCKS5/HTTP, учётные данные SOCKS5 и режим туннеля (ядерный TUN или userspace) из env-файла, принадлежащего root, запускает демон с той же командной строкой, что и приложение, и выставляет те же права на файлы (лог 644, сокет 666, каталог состояния 700). Строка `TS_VPN_BYPASS=0`, которую загрузочный скрипт раньше терял, записывается в кавычках, поэтому «Игнорировать другие VPN = выкл» переживает перезагрузку. Env-файл обновляется при каждом старте Root-режима, в том числе когда приложение присоединяется к демону, поднятому загрузочным скриптом.
- [x] **Падение демона больше не считается ручной остановкой (4.1.1):** флаг desired_running остаётся выставленным, если демон умер сам, поэтому автопереподключение перезапускает его в пределах лимита попыток; когда лимит исчерпан, служба уходит в отбой с уведомлением «нажмите, чтобы переподключиться», а 15-минутный сторож всё ещё может её оживить.

## 🔮 Планы

Состояние на 2026-10-14, к выпуску 5.0.0.

### Крупное

- [ ] **Удалённое управление, когда тейлнета нет, — спасательный канал через TailCat
      (следующая версия; первый кандидат в беты).** Попросил автор 2026-10-14. Сейчас
      сопряжённым устройством управляют только через тейлнет, поэтому в самый нужный момент
      до него не достучаться: истёк ключ, сервер координации для него заблокирован, служба
      остановлена или оно вошло в другой тейлнет. TailCat не требует аккаунта и уже возит
      ключ авторизации на телевизор (`TSP2:`), значит, может возить и API управления. Что
      решить до кода: кто на том конце без `whois` (остаётся только секрет сопряжения — от
      него и шифровать туннель насквозь, реле видит шифртекст); слушает ли управляемое
      устройство реле всегда или только пока лежит его тейлнет, чего это стоит и что
      раскрывает; и что разрешено через этот канал — посмотреть, перезапустить и передать
      новый ключ в правилах 5.0 записаны как «никогда удалённо», так что у канала будет свой
      короткий список, а не общий.
- [x] **Android TV (5.0.0, экспериментально).** Значок с баннером на главном экране телевизора
      для каждого варианта иконки; планшетная панель в роли главного экрана; всё достижимо
      пультом — заметная рамка фокуса, отступы от краёв, шторки и диалоги внутри безопасной
      области, поля ввода в виде строк с диалогом, длинные тексты листаются стрелками. Чего
      телевизор не умеет — скрыто (админ-консоль, сканер QR, подпись Tailnet Lock); что ему
      нужно редко — лежит в Настройки → Дополнительно. Вместо системного выбора файлов —
      встроенный обзор файлов и папок, ссылки без браузера показывают адрес и QR-код, а
      Настройки → Оформление → Интерфейс включает телевизионный интерфейс вручную.
      Пройдено на эмуляторах Android TV (API 36) и на WSA; **на настоящем телевизоре ещё не
      запускалось** — см. «Проверка на устройствах».
- [x] **Вход без клавиатуры (5.0.0).** Ссылка для входа в виде QR-кода на телевизоре и «Войти с
      другого устройства» на телефоне; ключ авторизации со сканера телефона на телевизор — по
      локальной сети или через реле TailCat, с кодом сверки на обоих экранах.
- [x] **Удалённое управление (5.0.0, экспериментально, по умолчанию выключено).** Устройство
      разрешает сопряжённым управлять своим TailSocks через тейлнет. Для сопряжения нужен
      шестизначный код с его экрана; устройство того же аккаунта — владелец, любое другое —
      гость на 24 часа. Два уровня, выбираются на самом управляемом устройстве: «Обычный
      доступ» (состояние, настройки подключения, выходной узел, принятые файлы, просмотр и
      запрос разрешений) и «Полный доступ» (его память со скачиванием файлов через Taildrop,
      общие папки, работа выходным узлом и маршруты, журнал без секретов) — включается только
      на устройстве и только для владельцев. Изменение, способное оборвать канал, условно:
      устройство вернёт прежнее значение, если управляющий не подтвердит за 60 секунд. Каждое
      изменение записывается на управляемом устройстве и показывается на его экране. Никогда
      удалённо: остановка насовсем, выход из аккаунта, сам аккаунт и сервер входа, любые
      учётные данные, прокси управления и обход блокировок, root-режим. Доступно в режиме
      прокси, в TUN на обоих движках и в root-режиме с ядровым TUN (патч 22 к демону держит
      порт в netstack, пока функция включена). Работает только внутри одного тейлнета;
      протокол объявляет свои возможности, так что сборки разных версий не ломаются, а
      показывают меньше.
- [x] **Taildrive, вторая половина (5.0.0).** Обзор общих папок других устройств и открытие их
      файлов в плеере через собственный провайдер приложения, с перемоткой по HTTP-диапазонам;
      когда список пуст, экраны говорят, что политика тейлнета разрешает этому устройству, а в
      визуальном редакторе политики есть шаблон для обмена между своими устройствами; один
      переключатель пускает локальную сеть в прокси Taildrive, пароль при этом обязателен.
- [x] **Поиск по настройкам (5.0.0).** Любая настройка по-русски и по-английски, с опечатками,
      не той раскладкой и транслитом; ссылки `tailsocks://settings/<раздел>/<строка>`. Тест
      читает исходники и падает, если строки нет в каталоге.
- [x] **Нативный TUN — опциональный движок (4.2.0).** Устройством `VpnService` владеет сам
      `tailscaled`, а не hev: `TunVpnService` поднимает туннель, мост перезапускает демона с
      `--tun=android-vpn` на унаследованном дескрипторе, роутер пустой, netstack оставляет себе
      только собственные потоки (патчи 17–19); в Настройки → TUN он тогда назывался
      «Нативный движок (экспериментальный)». Проверено на POCO: MagicDNS, split DNS, exit node и смена одного
      exit node на другой без разрыва, исключения LAN, одна карточка уведомления, один запуск
      демона при подключении (VPN поднимается первым по кешированным адресам). Заодно снят
      главный риск, вокруг которого писался план: SELinux разрешает приложению `TUNGETIFF` на
      дескрипторе туннеля (`allowxperm untrusted_app tun_device chr_file ioctl { 0x54D2 }`,
      прочитано с Redmi), а настоящий дочерний tailscaled выполнил `TUNGETIFF` и `SIOCGIFMTU`
      на унаследованном дескрипторе (проба из патча 17: `tun0`, флаги `0x1001`, MTU 1500).
- [x] **Нативный TUN — основной движок TUN (2026-10-12).** Режим приложения по умолчанию
      по-прежнему прокси; внутри режима TUN на нативном движке работают новые установки и все,
      кто движок не выбирал, а сохранённый `hev` остаётся hev (Настройки → TUN → Движок TUN;
      `hev-socks5-tunnel` — движок для совместимости, его настройки на месте). Что оставалось,
      сделано в коде: принятые subnet-маршруты без exit node попадают на устройство, их список
      собирается из статуса LocalAPI (оба движка; за exit node — только то, что не несут его
      маршруты по умолчанию: подсети внутри «Исключенных подсетей IP» и IPv6, пока весь IPv6 не
      идёт в туннель); старт, не нашедший адресов узла, поднимается, как только
      пришёл netmap; запуск always-on поднимает и само соединение; при выключенном «Использовать
      MagicDNS» устройство не получает DNS-сервера вместо quad-100, отвечающего SERVFAIL;
      устройство не лимитное; старт при остановленном соединении ничего не поднимает. Для
      Wi‑Fi ↔ LTE, doze и Android 7/8 явно неверного кода не нашлось; всё это — в «Проверке на
      устройствах». Остановить демона и поднять его на другом движке — задуманное поведение, а
      не долг; подмена дескриптора, `CallbackRouter` и `SCM_RIGHTS`, за которые выступает
      [`NATIVE_TUN_PLAN.md`](NATIVE_TUN_PLAN.md) (только на английском), остаются амбицией
      того документа, оставлены там для истории и здесь не нужны.
- [ ] **tsnet — идея, в 5.0 не взята.** Демон внутрь процесса приложения. Несовместимо с Root-режимом,
      где он обязан быть отдельным процессом под `su`.
- [x] **Один бинарник вместо двух (2026-10-12).** Вариант (e) бывшего пункта «Отдельный
      CLI-бинарник»: `libtailscale.so` собирается с апстримовским тегом `ts_include_cli` и
      заодно является CLI — работает как `tailscale`, когда его argv[0] равен `tailscale`
      (ссылка в каталоге данных, теперь указывающая на демона) или когда задан `TS_BE_CLI=1`
      (обёртка Root-режима: shell не умеет переносимо задавать argv[0]). `libtailscale_cli.so`
      больше нет. Измерено: на устройстве 40.0 → 28.0 МБ на arm64, 39.0 → 27.1 на armeabi-v7a,
      39.3 → 27.3 на x86, 43.2 → 30.2 на x86_64 (около −12 МБ на каждой); релизные APK против
      4.9.1 теряют 4.4–5.1 МБ на ABI (arm64 31.3 → 26.9 МБ) и 19 МБ универсальный
      (105.0 → 86.0 МБ). Поведение CLI — апстримовское, проверено на сборке под хост с теми же
      тегами: ссылка `tailscale` и `TS_BE_CLI=1` дают CLI, любое другое имя — демона. Осталось
      проверить на устройстве Консоль и обёртку Root-режима (`su -c tailscale status`).
  - Замечание: `useLegacyPackaging` отключить нельзя — демон запускается через `exec()` из
    `nativeLibraryDir`, а для этого библиотеки должны быть распакованы на диск.

### Требует решения автора

- [x] **Честная ОС — что выяснило исследование (2026-09-07).** Патч 06 подставляет `OS = linux`
      исходя из того, что координатор игнорирует объявленные сервисы у андроидных узлов. Это не
      подтвердилось: в клиенте нет ни одной проверки `Hostinfo.OS` для serve, funnel или cert —
      единственные ворота это узловые capability `https` и `funnel`, приходящие в netmap.
      Настоящие андроидные ворота — сборочный тег `!android` на `ipn/localapi/cert.go`, и его уже
      снимает патч 05, то есть Serve/Funnel работали не благодаря маскировке. peerAPI и Taildrop
      не затронуты: узел `Pixel 8` с `OS = android` в этой сети объявляет `peerapi4`/`peerapi6`,
      а в коде отказ прописан только для tvOS. Единственное задокументированное последствие
      честности — device posture: `node:os` переключается с linux на android. Апстримный
      `tailscale/tailscale#18245` показывает узел с `OS = android`, получающий сертификаты от
      координатора. Сам переключатель уже сделан (см. «Завершённые этапы», по умолчанию выключен).
      **Измерено 2026-09-07 на Redmi:** в маскараде у узла есть `https` и `funnel`, Funnel отвечает
      из публичного интернета за 5 с, `tailscale cert` выдаёт сертификат, координатор забирает
      список сервисов по c2n; честно — для того же узла (зарегистрированного как Linux) координатор
      отвечает «node OS changed since last connection, was node state copied between devices?»,
      не отдаёт netmap и capabilities, `cert` падает. Значит, зарегистрированный узел
      сменить ОС не может. Вторая половина прошла в тот же день на новом профиле: узел, с самого
      начала зарегистрированный как Android, держит `https` и `funnel`, `tailscale cert` выдаёт
      сертификат, Funnel отвечает HTTP 200 из публичного интернета за 5 с, а консоль
      администратора называет машину по модели устройства (`xiaomi-23030rac7y`, «Android (16)»).
      Отсюда настройка — свойство профиля, фиксируемое при создании. Решено
      2026-09-07: для новых профилей по умолчанию выключено, маскировка остаётся нормой.
- [x] **Задача #3** — отвечена и закрыта; Root-режим и есть то, о чём она просила.

- [x] **Слишком «узкая» сеть теперь называется (5.0.0).** Проверка сети предупреждает, когда
      MTU интерфейса меньше, чем нужно пакету тейлнета в обёртке WireGuard (1360, по IPv4 —
      1340), а отчёт диагностики всегда называет интерфейс и его MTU. Найдено на WSA, где

      ответ становится предупреждением в Root-логе и строкой в отчёте диагностики вместо
      молчания. Остаётся и меряется только на таком устройстве: уходит ли запрос по IPv6 мимо
